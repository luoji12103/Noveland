# v1.0.6 Beta Feedback System Plan

Date: 2026-05-20
Branch: feature/v1.0-6-beta-feedback
OpenSpec change: `openspec/changes/v1-0-private-beta-mvp/`

## Decision Summary

Phase 6 will use a dedicated beta feedback boundary instead of extending moderation as the
primary record owner. Moderation remains available for later safety or abuse escalation, but beta
feedback has a different lifecycle: private tester reports, issue taxonomy, contextual gameplay
evidence, admin triage, and repair-proposal linkage.

This keeps feedback from becoming a public forum, avoids overloading incident workflows, and lets
Phase 7 bridge feedback into authoring repair proposals without automatic mutation.

## Ownership

- Package owner: `backend/packages/beta_feedback/`
- API owner: `backend/services/api/src/noveland/services/api/beta_feedback.py`
- Router registration: app-level include only
- Primary table: `beta_feedback_reports`
- Route shape: `/worlds/{world_id}/beta-feedback/reports`
- Access:
  - private beta/world members may create reports and list/read their own reports
  - world admins and platform admins may list/read all reports and triage
  - other testers never see reporter-private data
- No broad `worlds.py` route growth

## Issue Taxonomy

Phase 6 will support beta issue types for:

- dialogue
- persona
- memory
- sprite
- background
- voice
- playback
- provider
- quota
- session recovery
- UX
- worldline
- other

Severity starts at low/medium/high/critical. Status starts at submitted and moves through triaged,
investigating, linked_to_repair, resolved, or dismissed by explicit admin triage.

## Safe Evidence Refs

Feedback may link to safe IDs only:

- worldline
- scene
- conversation
- turn
- presentation
- media asset or media job
- model invocation
- persona
- memory
- voice profile
- sprite set or sprite variant
- background profile
- provider integration
- player actor
- quota/session/UX markers

The service will validate same-world and same-worldline ownership where the referenced record is
worldline-scoped. Non-admin reporters cannot reference hidden or developer-only media/voice/visual
records. Responses include IDs and labels only, never raw prompt snapshots, provider payloads,
storage/object paths, bytes/base64, raw prompt/output text, resolved secrets, or invite tokens.

## Frontend Scope

Phase 6 includes a minimal operational Web surface because testers need a feedback entry point and
admins need triage:

- tester feedback form and own report list
- admin all-report list and triage form
- no public forum, comments, social feed, or attachment browser
- no graph/editor surfaces

`impeccable` has been used before implementation. The UI will reuse existing workspace/admin form,
notice, list, and table vocabulary.

## Repair Linkage

Phase 6 may store safe repair proposal refs on triage, but it will not create or apply repair
proposals. Phase 7 owns the bridge from feedback/diagnostics to authoring preview/review/apply.

## Tests

Targeted tests should cover:

- feedback create/list/read for tester-owned records
- admin list/read/triage
- reporter privacy across testers
- issue taxonomy/status/severity validation
- same-world and same-worldline evidence validation
- hidden/developer-only evidence rejection for non-admin reporters
- repair-proposal refs are safe links only
- no world event writes
- no raw prompt/output, prompt snapshot, storage/path, bytes/base64, secret, or token leaks
- Web feedback form and admin triage interactions

## Stop Conditions

Stop implementation if:

- feedback requires public forum, social feed, or cross-tester discussion behavior
- safe evidence cannot represent the needed context without raw prompt/output, prompt snapshot
  internals, storage paths, bytes/base64, resolved secrets, or invite tokens
- reporter private data must be visible to other testers
- feedback repair linkage would automatically mutate world state or bypass authoring review/apply
- implementation requires broad `worlds.py` route growth
- Web UI becomes necessary and `impeccable` cannot be used
