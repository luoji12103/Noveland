# v0.4.2 Provider Admin Console Plan

## Goal

Implement the v0.4 Provider Admin Console for Phase 5+ provider integrations. World admins should be able to inspect and manage allowed provider integrations, capabilities, health-check history, smoke-test status, auth_ref status, and restricted visibility without exposing resolved secrets or changing provider execution behavior.

## Route Decision

- Keep existing `/admin/providers` as the legacy platform model-provider-profile admin surface.
- Add a new world-scoped Web route at `/worlds/{worldId}/providers` for `provider_integrations`.
- Use the existing `/api/worlds/[...worldPath]` same-origin proxy to call backend `/worlds/{world_id}/providers`.
- Add a `Providers` link to the world workspace nav.

This avoids converting `provider_profiles` into the universal provider registry and keeps the Phase 5 provider boundary explicit.

## Scope

- Add Web types and client helpers for provider integrations, capabilities, health checks, and smoke tests.
- Add a server data loader for world provider admin data.
- Add a world-scoped provider console component.
- Support provider list/detail, create/update/delete, capabilities, health-check history, health-check action, smoke-test action, auth_ref reference status, and restricted visibility display.
- Reuse v0.4.1 admin foundation components and same-origin admin/client patterns.
- Add focused Web unit tests for client helpers, component behavior, and route/proxy expectations.

## Non-goals

- No backend provider kernel changes.
- No migrations.
- No new provider adapters.
- No resolved secret display.
- No Web UI for media/visual/speech/invocation/diagnostics phases.
- No public reader/player provider exposure.

## Guardrails

- Treat `auth_ref` only as an opaque reference string.
- Do not render resolved secret values, Authorization headers, raw prompt/output data, storage URIs, file paths, bytes, or base64.
- Do not use `provider_key`, `config_json`, or naming inference for execution dispatch.
- Do not bypass backend ACLs. Backend world-admin/provider APIs remain authoritative.
- Restricted visibility must be displayed as restricted state and only requested through existing backend permission behavior.
