# v0.7.2 Secret & Provider Governance Plan

## Goal

Harden provider execution boundaries so disabled providers cannot execute and provider authentication remains an opaque `auth_ref` reference through create, update, health, smoke, execution, diagnostics, and ledger paths.

This phase is backend/API/test focused. It should close governance gaps in the existing provider, image, speech, and narrative quality execution paths without adding new provider capabilities.

## Scope

- Enforce disabled/non-active provider blocking before any external provider call.
- Cover provider execution boundaries:
  - direct provider execution and smoke tests
  - image generation/edit/compose provider dispatch
  - speech TTS/STT provider dispatch
  - narrative quality provider-backed generation
- Confirm `auth_ref` rotation persists only the reference string and never resolved secret values.
- Ensure provider health, invocation metadata, prompt snapshots, diagnostics, and API responses use safe status/reason evidence only.
- Add focused regressions for disabled provider blocking and secret redaction.
- Reuse existing provider registry, secret resolver, health service, execution service, invocation ledger, and API authorization dependencies.

## Non-goals

- No full vault/KMS or encrypted database secret storage.
- No provider marketplace.
- No client-side secret management UI.
- No new provider adapters or provider business features.
- No Web UI.
- No streaming.
- No broad `worlds.py` route growth.
- No new public reader/player delivery path.

## Deliverables

- Disabled provider execution blocked at provider, image, speech, narrative quality, and smoke-test paths.
- Auth reference rotation regression coverage.
- Safe provider evidence and response redaction regression coverage.
- Updated OpenSpec Phase 2 task status and harness docs after implementation.

## Guardrails

- `provider_integrations.auth_ref` is an opaque reference only.
- Resolved secrets must never be persisted or returned.
- Secrets must not appear in `model_invocations`, `prompt_snapshots`, `media_jobs`, provider health metadata, diagnostics, logs, or API responses.
- Disabled provider blocking must happen before external network/provider calls.
- Blocked execution may record safe evidence only: status, reason code, provider id, capability, and auth-reference presence/resolution booleans.
- Do not write raw prompts, raw outputs, storage URIs, filesystem paths, bytes, base64, or resolved secrets into `world_events.payload`.

## Stop Conditions

- Disabled provider enforcement requires a broad router rewrite or broad `worlds.py` change.
- The current provider status model cannot represent active/disabled/deleted semantics safely.
- Secret rotation cannot be validated without storing or exposing resolved secrets.
- Provider execution, image, speech, or narrative quality paths require raw prompt/output or secret exposure to produce evidence.
- Targeted tests or the full local gate fail.

## Targeted Tests

- Disabled provider cannot execute through direct provider execution.
- Disabled provider cannot execute through smoke test.
- Disabled provider cannot execute through image service/provider dispatch.
- Disabled provider cannot execute through speech service/provider dispatch.
- Disabled provider cannot execute through narrative quality provider-backed paths.
- Rotating `auth_ref` stores and returns only the reference string.
- Provider API responses, health metadata, invocation metadata, and prompt snapshots do not include resolved secret values.
- Existing fake provider flows continue to work when the provider is active.

## Validation
