# v0.9 Self-use MVP Demo World Cut Feasibility Review

## Scope

This review evaluates whether current `main` can support the active OpenSpec change `openspec/changes/v0-9-self-use-mvp-demo-world-cut/`. It is documentation-only: no backend behavior, Web behavior, migrations, API routes, or runtime contracts were changed.

## Conclusion

Implementation recommendation: start with v0.9 as a single change, but do not treat it as fully ready for blind execution. Phase 1 can start after its docs-only checkpoint confirms provider template and model discovery ownership. Phase 2 must make an explicit package/router/schema decision before implementation.

Recommended status: revise implementation plan during phase checkpoints, not the overall OpenSpec roadmap.

Required decisions before implementation:

- Provider text execution: decide whether v0.9 Phase 1 implements `OPENAI` / `OPENAI_COMPATIBLE` / `ANTHROPIC` / `ANTHROPIC_COMPATIBLE` text adapters in `ProviderExecutionService`, or limits Phase 1 to settings/templates plus fake smoke until a text adapter subtask lands.
- Model discovery: decide the first contract for model-list discovery, including provider endpoint config, redaction, manual fallback, and no default external calls.
- Visual Generation Control Plane ownership: create a dedicated `backend/packages/visual_generation/` package and `backend/services/api/src/noveland/services/api/visual_generation.py` router for workflow templates, inventory, character visual generation profiles, and provider-neutral generation plans.
- Persona card target: store reviewed persona output primarily in `AgentPersona`; use `Agent.character_profile` for structured character fields and memory write/apply paths for long-term memory candidates.

## Current Capability Map

### Provider Settings & Model Lab

Existing support:

- `provider_integrations` already has `provider_kind`, `adapter_kind`, `base_url`, `auth_ref`, `config_json`, `default_params_json`, status, visibility, and capabilities.
- `ProviderKind` covers text generation, image generation/editing/analysis/composition, speech-to-text, text-to-speech, voice cloning, workflow engine, embedding, reranker, and other.
- `ProviderAdapterKind` includes `OPENAI`, `OPENAI_COMPATIBLE`, `ANTHROPIC`, `ANTHROPIC_COMPATIBLE`, `COMFYUI`, `MIMO_TTS`, `MIMO_ASR`, `CUSTOM_HTTP`, and local/fake adapters.
- `ProviderSecretResolver`, `reject_sensitive_config`, `sanitize_for_persistence`, budget checks, health checks, smoke tests, invocation ledger, prompt snapshots, and media-output writes already exist.
- The Web admin provider integration surface supports provider CRUD shape, adapter/provider kind selection, base URL, auth ref, config JSON, capabilities, health, and smoke test.

Gaps:

- Model-list discovery was not found as a service/router/UI contract.
- Settings-facing templates/presets for OpenAI-compatible LLM, Anthropic-compatible LLM, MiMo, Z-Image, GPT Image, ComfyUI, and generic image APIs are not productized.
- `ProviderExecutionService._adapter_for()` routes `OPENAI_COMPATIBLE` to the image adapter, and does not implement Anthropic text adapters. Routing declares compatibility for text, but execution is not aligned.
- Z-Image has no distinct adapter/preset. It can likely start as OpenAI-compatible image or custom HTTP with a Z-Image template, but a dedicated adapter should be a later explicit decision.

### Visual Generation Control Plane

Existing support:

- ComfyUI adapter exists and can execute configured workflow/request data.
- `asset_generation` already has preview/apply runs, proposals, policy JSON, provider preferences, media job creation, and no-leak JSON validation.
- `media`, `visual`, `reader_delivery`, provider execution, invocation ledger, package contracts, and authoring proposals provide most adjacent primitives.

Gaps:

- No workflow-template registry with versions and parameter slots.
- No visual model inventory for checkpoint, LoRA, VAE, embedding, ControlNet, IP-Adapter, workflow template, or prompt preset metadata.
- No character/worldline visual generation profile.
- No provider-neutral visual generation plan DTO or validator.
- Current ComfyUI execution is too low-level for the v0.9 safety model; raw workflow-like request data must be mediated by templates and slots before runtime use.

### Galgame Source Intake

Existing support:

- `backend/packages/authoring/` owns source batches, source assets, source fragments, import runs, proposals, review decisions, source traceability, preview, and apply.
- Source assets may reference `media_asset_id`, and source fragments preserve safe excerpts, locator JSON, metadata, world, and worldline.
- Authoring JSON validators reject leaky keys such as storage paths, base64, raw prompt/output/source markers, and filesystem path keys.

Gaps:

- No directory intake scanner for already-unpacked galgame asset trees.
- Existing source asset kinds are broad (`image`, `audio`, `script`, etc.); VN-specific roles such as sprite, expression, CG, BGM, SE, route file, and profile sheet should live in metadata/proposals unless a migration is approved.
- Large raw scripts cannot fit entirely in `excerpt_text`; intake needs fragmenting and source locators.

### Script Dialogue Extraction

Existing support:

- v0.5 deterministic script parsing already creates dialogue, scene, choice, route, and event proposals without canon mutation.
- Authoring proposals are worldline-scoped and reviewable.

Gaps:

- Current deterministic parser is not a full galgame/VN parser.
- Provider-backed extraction is not first-line and should remain optional until provider text execution is aligned.
- Script fragments should stay in authoring source/proposals; do not introduce a second parser store in v0.9.

### Character Memory Distillation Agent

Existing support:

- Provider invocation ledger and prompt snapshots exist.
- Authoring memory migration proposals exist.
- `AgentPersona` has `persona_text`, behavior policy, plugin identifier/config, and enabled flag.
- `Agent.character_profile` can carry structured character metadata.
- Memory services and queues exist for reviewed memory writes/backfill/readiness.

Gaps:

- There is no provider-backed distillation service that reads source fragments and writes persona/memory proposals.
- Apply path from authoring proposals into `AgentPersona`, `Agent.character_profile`, and memory records must be designed carefully.
- Raw full scripts must not be copied into runtime prompts or broad proposal payloads.

### Visual Asset Mapping

Existing support:

- `backend/packages/visual/` owns `CharacterSpriteSet`, `CharacterSpriteVariant`, and `SceneBackgroundProfile`, all worldline-scoped.
- Visual resolver handles sprite/background lookup and suppresses restricted visibility for non-admin use.
- Visual records already link to media assets and can be used by v0.8 playback/scene UI.

Gaps:

- No imported galgame asset classifier/matcher beyond existing authoring asset matching.
- No CG-specific mapping model beyond media roles/metadata and possible scene/background/composite conventions.
- Mapping should remain proposal/review/apply; do not directly mutate visual bindings during intake.

### Voice Profile Mapping

Existing support:

- `backend/packages/speech/` owns voice profiles, agent voice profile bindings, speech style mappings, transcripts, TTS, and STT.
- Voice profiles are worldline-scoped and can reference provider integration and media reference assets.
- MiMo TTS/ASR adapters exist and are configured through provider `base_url`, `auth_ref`, and JSON fields.

Gaps:

- MiMo provider templates and UI presets are not productized.
- TTS/ASR smoke behavior exists through provider/speech paths, but model-list discovery and manual model fallback are not first-class.
- Voice reference import from galgame audio needs authoring proposals before profile/binding apply.

### Demo World Assembly

Existing support:

- Authoring preview/apply, world packaging import preview/apply, media, visual, speech, conversation presentation, scene view, reader playback, memory, and worldline primitives exist.
- v0.8 sample world packaging fixture can inform deterministic assembly evidence.

Gaps:

- No dedicated demo-world assembly service that turns reviewed proposals into a minimal 2-3 character world path.
- World creation/import/apply paths are split across worlds, authoring, packaging, visual, speech, and memory; v0.9 needs an orchestration layer or authoring sub-service.

### 30-Minute Self-use MVP Gate

Existing support:

- Observability/readiness gates exist for production and public launch.
- Multimodal evals, narrative quality evals, memory readiness, provider health, media jobs, invocation ledger, reader playback, and scene UI provide evidence sources.

Gaps:

- No self-use MVP gate/checklist tailored to 30-minute continuity, resume, provider fallback, memory retention, and demo-world playability.
- This should start as admin-only evidence aggregation plus manual checklist, not a new public gate.

## Gaps By Phase

### Phase 1 — MVP Provider Settings & Model Lab

Can start first, but only after the checkpoint confirms:

- provider templates are code/static manifests over the existing provider registry, not a second provider system;
- model discovery contract and safe failure/manual fallback;
- text adapter scope and whether real text execution is included in Phase 1;
- `impeccable` use before Web settings/model lab UI implementation.

Expected migration: likely none if templates are static/code-owned and discovery is non-persistent. Stop if persistent template/model-list records are required.

### Phase 2 — Visual Generation Control Plane

Requires new schema and bounded ownership. Existing `visual` and `asset_generation` are adjacent but not sufficient owners:

- `visual` owns applied sprite/background bindings;
- `asset_generation` owns lookahead generation proposals/jobs;
- `providers` owns execution and adapters;
- new `visual_generation` should own templates, inventory, profiles, planning, and validators.

Expected migration: likely required for workflow templates, visual model inventory, character visual generation profiles, and generation plan/evidence records.

### Phase 3 — Provider Worktree Integration Test Harness

Feasible as docs/tests. It should be default-skip and use fake/mocked providers in normal gates.

Expected migration: none.

### Phase 4 — Galgame Source Intake

Feasible using authoring plus media, but directory scanning and metadata conventions need implementation. Keep already-unpacked source-only legal boundary.

Expected migration: avoid initially by using authoring metadata/proposals. Stop if VN-specific source role columns become required.

### Phase 5 — Script Dialogue Extraction

Feasible if deterministic parser comes before provider extraction. Keep provider extraction optional until text execution alignment is complete.

Expected migration: none initially.

### Phase 6 — Character Memory Distillation Agent

Feasible, but needs provider text execution and persona/memory apply decisions. Use authoring proposals for persona card, structured profile fields, relationship summaries, and memory candidates.

Expected migration: possibly none for first version if `AgentPersona`, `Agent.character_profile`, authoring proposals, and memory services are enough. Stop if source-linked persona revisions need dedicated tables.

### Phase 7 — Visual Asset Mapping

Feasible by extending authoring asset matching into visual apply paths. Imported assets should become media assets first, then reviewed visual bindings.

Expected migration: likely none if using existing visual tables and proposal payloads.

### Phase 8 — Voice Profile Mapping

Feasible by reusing speech profiles/bindings/style mappings. MiMo gaps belong mostly to Phase 1 provider templates and adapter smoke coverage.

Expected migration: likely none.

### Phase 9 — Demo World Assembly

Feasible through authoring orchestration. Prefer an authoring assembly service/router extension, not broad `worlds.py` growth.

Expected migration: maybe none for first self-use assembly if it writes existing world/agent/persona/memory/visual/speech/conversation records through reviewed apply.

### Phase 10 — 30-Minute Self-use MVP Gate

Feasible using observability/readiness patterns. Do not duplicate production/public readiness; add an admin-only self-use gate/evidence report under observability or authoring diagnostics after phase checkpoint.

Expected migration: none unless persisted gate runs are required.

## Recommended Phase Order

Keep the OpenSpec order:

1. MVP Provider Settings & Model Lab
2. Visual Generation Control Plane
3. Provider Worktree Integration Test Harness
4. Galgame Source Intake
5. Script Dialogue Extraction
6. Character Memory Distillation Agent
7. Visual Asset Mapping
8. Voice Profile Mapping
9. Demo World Assembly
10. 30-Minute Self-use MVP Gate

Do not move provider lab ahead of Phase 2. The lab should test the contracts created by provider settings and visual generation control, especially ComfyUI dry-run/mock validation.

## Package / Router Recommendations

- Provider settings/model lab: extend `backend/packages/providers/` and `backend/services/api/src/noveland/services/api/providers.py`; do not create a second provider registry.
- Visual generation control plane: add `backend/packages/visual_generation/` and `backend/services/api/src/noveland/services/api/visual_generation.py`; reuse media/provider/visual/authoring rather than placing this in `worlds.py`.
- Galgame source intake, script extraction, memory distillation proposals, visual/voice mapping proposals, and demo assembly: extend `backend/packages/authoring/` and `authoring.py` where the boundary is proposal/review/apply.
- Applied sprite/background binding remains in `backend/packages/visual/`.
- Applied voice profile/binding remains in `backend/packages/speech/`.
- Self-use MVP gate should reuse `backend/packages/observability/` unless the phase checkpoint proves authoring owns the evidence better.

## Provider Adapter Gaps

- Implement or explicitly defer text generation adapters for OpenAI-compatible and Anthropic-compatible execution. Current declarations are broader than actual adapter execution.
- Add model discovery service and router actions with no client-side secrets, no default external calls, safe error shape, and manual model fallback.
- Add provider templates for OpenAI-compatible LLM, Anthropic-compatible LLM, MiMo TTS/ASR, Z-Image, GPT Image, ComfyUI, OpenAI-compatible image, and generic image/custom HTTP.
- Treat Z-Image as a template over compatible/custom image execution first unless implementation research shows a dedicated adapter is necessary.
- Keep MiMo base URL configurable to support newapi distribution.

## Frontend Gaps

- Provider settings/model lab needs a productized settings/admin UI beyond the current JSON-heavy provider integration console.
- Visual generation control surfaces, import preview, mapping review, voice mapping, and demo assembly likely require Web UI in later phases.
- Use `impeccable` before any Web implementation phase that adds or reshapes UI. Keep v0.9 UI operator-grade: dense, explicit, stateful, and not a marketing or game landing page.

## Risks And Stop Conditions

Stop before implementation or within a phase if:

- provider text execution cannot be made ledger-backed and secret-safe;
- model discovery requires exposing API keys to the browser;
- ComfyUI support requires arbitrary runtime workflow JSON execution;
- visual generation schema ownership conflicts with provider/media/visual/asset_generation boundaries;
- source intake requires storing filesystem paths or raw source in reader-visible records;
- provider output would directly mutate canon, memory, visual bindings, voice bindings, or world state;
- persona card apply cannot preserve source traceability and review/apply;
- worldline isolation for source, visual profile, memory, voice, or demo assembly is unclear;
- any response leaks `storage_uri`, filesystem/object paths, bytes, base64, raw prompt, raw output, prompt snapshot internals, or resolved secrets;
- frontend work is needed but `impeccable` cannot be used/read.

## Implementation Recommendation

Proceed with v0.9, but begin with a Phase 1 planning checkpoint that records:

- provider templates are static/code-owned unless a migration is explicitly approved;
- model discovery is best-effort and manual-model fallback is required;
- text adapter execution alignment is part of Phase 1 or explicitly split as the first Phase 1 subtask;
- no real provider tests run by default.

Before Phase 2 implementation, record a schema decision for a dedicated `visual_generation` package/router and add the migration plan. Without that decision, Phase 2 should block.
