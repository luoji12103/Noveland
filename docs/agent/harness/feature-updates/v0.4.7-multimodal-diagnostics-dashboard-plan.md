# v0.4.7 Multimodal Diagnostics Dashboard Plan

## Goal

Implement the v0.4 Multimodal Diagnostics Dashboard so world admins can review Phase 12 multimodal diagnostic results, run the existing multimodal smoke eval, inspect recent eval runs, and understand blocker/warning status from the Web workspace without changing backend diagnostic rules or exposing secrets, storage paths, raw prompts, or raw outputs.

## Route Decision

- Add a world-scoped Web route at `/worlds/{worldId}/diagnostics`.
- Use the existing `/api/worlds/[...worldPath]` same-origin proxy for backend multimodal diagnostics and eval-run API calls.
- Add a `Diagnostics` link to the world workspace nav.
- Keep existing world overview/runtime diagnostics unchanged.

## Scope

- Add Web types and client helpers for:
  - `GET /worlds/{world_id}/diagnostics/multimodal`;
  - `GET /worlds/{world_id}/multimodal-evals`;
  - `POST /worlds/{world_id}/multimodal-evals/run`;
  - `GET /worlds/{world_id}/multimodal-evals/{run_id}` if useful for detail refresh.
- Add a server data loader for diagnostics admin data using worlds, memberships, worldlines, current diagnostics, and recent multimodal eval runs.
- Add a multimodal diagnostics dashboard component with:
  - status overview for diagnostic status, blocker count, warning count, recommendation count, recent run count, and selected worldline;
  - blocker and warning tables grouped by code/severity/message/evidence references;
  - provider health, media job/object, invocation cost/latency, sprite/background, voice, transcript, sample fixture, and leak-check summaries from safe metrics;
  - recent eval-run list showing status, eval key, worldline, timestamps, safe metrics, blockers, and recommendations;
  - explicit `Run multimodal smoke eval` action using the existing backend eval endpoint.
- Reuse v0.4.1 admin foundation components and existing backend multimodal eval APIs.
- Add focused Web unit tests for client helpers, dashboard rendering, eval-run action, workspace navigation, and leak-safe rendering.

## Non-goals

- No backend diagnostic rule changes.
- No migrations.
- No duplicate release/eval framework.
- No public launch gate changes.
- No provider execution, provider configuration, new provider adapters, or live smoke-test behavior changes.
- No asset generation, daemon behavior, streaming, public reader delivery, or Web media playback.
- No raw prompt/output display, resolved secret display, storage URI/path display, base64 display, or raw bytes display.
- No `worlds.py` route refactor.

## Guardrails

- The dashboard must rely on backend world-admin ACLs and must not bypass diagnostic/eval permission checks.
- Evidence references should show kind/id/count/status only; they must not render raw prompts, raw outputs, storage URIs, filesystem paths, resolved secrets, raw bytes, or base64 payloads.
- Metrics and metadata rendering must recursively sanitize secret-like keys and path-like/media-uri/base64-like values before display.
- Eval-run creation must be explicit and admin-triggered; it must not start background daemon work or provider calls beyond the existing backend eval service.
- The page must make worldline, eval key, release/eval reuse, provider, media, invocation, visual, speech, and leak-check boundaries visible.
