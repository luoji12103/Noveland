# v1.0.7 Beta Content Iteration Loop Plan

Date: 2026-05-20
Branch: feature/v1.0-7-beta-content-iteration
OpenSpec change: `openspec/changes/v1-0-private-beta-mvp/`

## Decision Summary

Phase 7 will not add a new repair framework. Beta feedback and memory/persona QA diagnostics will
be converted into existing authoring import proposals, then existing authoring review/apply remains
the only mutation path.

This keeps the private beta iteration loop aligned with the v0.5/v0.9 authoring boundary: feedback
and diagnostics may propose persona, memory, dialogue-style, visual, voice, provider-profile, or
visual-generation-profile repairs, but no repair is applied automatically.

## Ownership

- Package owner: `backend/packages/authoring/`
- API owner: `backend/services/api/src/noveland/services/api/authoring.py`
- Feedback evidence owner: `backend/packages/beta_feedback/`
- Primary persistent records: existing `authoring_import_runs`, `authoring_import_proposals`,
  `authoring_review_decisions`, and `beta_feedback_reports.repair_proposal_refs`
- Router registration: existing app-level authoring router only
- No new package, no new migration, and no broad `worlds.py` route growth

## Repair Inputs

Phase 7 may create repair proposals from:

- beta feedback reports in the same world/worldline
- memory/persona QA finding refs
- safe diagnostic refs
- admin-authored repair candidates

Inputs are IDs, labels, summaries, issue categories, and safe metadata only. They must not include
raw prompts, raw provider outputs, prompt snapshot internals, storage/object paths, bytes, base64,
resolved secrets, invite tokens, or raw source blobs.

## Candidate Mapping

The first implementation will map repair kinds onto existing proposal kinds and target refs:

- `persona`: `character` proposal with `agent_persona_candidate`
- `memory`: `memory` proposal with `memory_candidate`
- `dialogue_style`: `other` trace-only proposal with `dialogue_style_repair_candidate`
- `sprite_binding`: `asset_match` proposal with `sprite_asset_match`
- `voice_binding`: `asset_match` proposal with `voice_asset_match`
- `background_binding`: `asset_match` proposal with `background_asset_match`
- `provider_profile`: `other` trace-only proposal with `provider_profile_repair_candidate`
- `visual_generation_profile`: `asset_match` trace-only proposal with
  `visual_generation_profile_recommendation`

Persona, memory, sprite, voice, and background repairs may apply only through existing authoring
apply support after explicit approval. Dialogue-style and provider-profile repairs are trace-only
until a later OpenSpec change defines a safe target mutation.

## API Scope

Add one admin-only endpoint under the existing authoring router:

- `POST /worlds/{world_id}/authoring/beta-content-repairs`

The endpoint creates a preview import run plus proposed repair records, links safe feedback reports
to the created proposal refs, and returns an impact report. Review and apply continue through the
existing authoring review/apply endpoints.

## Frontend Scope

No Phase 7 Web UI is scoped. Admin repair review continues through existing authoring APIs. If a
later UI is requested for repair review, implementation must read and use `impeccable` first.

## Tests

Targeted tests should cover:

- out-of-character feedback creates a persona repair proposal
- memory repair proposal preserves feedback/source traceability
- sprite, voice, and background repair proposals reuse existing asset-match targets
- provider-profile repair remains trace-only
- visual generation profile repair remains reviewable/trace-only
- repair proposals do not mutate persona, memory, visual, speech, provider, or world state before
  explicit review/apply
- existing reviewed apply still works for supported persona, memory, visual, and voice targets
- cross-world and cross-worldline feedback refs are rejected
- feedback report `repair_proposal_refs` are linked with safe proposal refs
- no world event writes and no forbidden data leaks in responses

## Stop Conditions

Stop implementation if:

- repairs require direct mutation outside authoring review/apply
- feedback or QA evidence cannot be represented without raw prompts, raw outputs, prompt snapshot
  internals, storage/object paths, bytes/base64, resolved secrets, invite tokens, or raw source
  blobs
- Phase 7 would require a duplicate repair package/framework
- applied repair would lose source, diagnostic, or feedback traceability
- implementation requires broad `worlds.py` route growth
- Web UI becomes necessary and `impeccable` cannot be read/used
