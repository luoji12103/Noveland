# v0.8.5 Scene View / Galgame View Plan

Date: 2026-05-16
Branch: `main`

## Scope

Implement the first authenticated reader/player scene view over existing conversation turns, conversation turn presentations, and Phase 1 reader-safe media descriptors. The view should present a basic galgame-style reading surface with scene imagery, dialogue, turn state, and optional audio.

## Accepted Design

- Add a reader/player Web route under the conversation reader surface, preferably `/worlds/{world_id}/reader/conversations/{conversation_id}/scene`.
- Reuse the Phase 2 conversation playback data loader and reader-safe media descriptor resolution where practical.
- Display one active turn at a time with a stable background/composite/sprite image area, subtitle/dialogue text, turn list controls, and optional audio controls.
- Use reader-safe media object download URLs only.
- Prefer composite scene image, then background image, then any reader-visible turn image. Show deterministic fallbacks when image/audio is missing.
- Keep all state local to the Web UI. Do not mutate conversation turn presentations or worldline state.

## Non-Goals

- No full game engine.
- No custom rendering or second media compositor.
- No complex animation system.
- No provider calls.
- No direct admin media API usage.
- No public unauthenticated access.
- No raw prompt/output, storage URI, filesystem path, base64, bytes, resolved secret, or raw internal event payload display.
- No editing/authoring controls.

## Current Capability Inventory

- Phase 1 provides authenticated reader-safe media descriptors and application-mediated object download URLs.
- Phase 2 provides `ConversationPlaybackData`, `getConversationPlaybackData()`, and turn/presentation/media resolution patterns.
- Existing e2e mock data includes a reader-visible conversation, presentation image, and missing-media fallback turn.
- `ConversationPlayback` already verifies that reader media is visible and no admin media DTO/storage path leaks into the playback page.

## Implementation Notes

- Use `impeccable` context before editing Web UI files.
- Keep the UI restrained and reader-focused: one stage, one subtitle area, turn controls, optional audio, and clear missing-media states.
- Add a link from the existing playback surface to scene view if it helps discoverability.
- Keep reduced-motion-friendly transitions; avoid choreography or layout animation.
- Use stable dimensions for the scene stage so media/fallback/loading state does not shift layout.
- Keep tests focused on visibility, safe media use, fallback behavior, and no leak markers.

## Targeted Validation

- Web component tests for scene rendering, turn switching, safe fallback states, optional audio, and no destructive/editing controls.
- E2E smoke proving an authenticated reader/member can open the scene view, see background/dialogue, switch to a missing-media turn, and avoid leak markers.
- Web lint, Web typecheck, focused tests, OpenSpec strict validation, and `git diff --check`.
- Full local gate after implementation.
