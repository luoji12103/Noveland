# v1.0 Private Beta MVP Feasibility Review

## Scope

This review evaluates whether current `main` can support the active OpenSpec change
`openspec/changes/v1-0-private-beta-mvp/` after v0.9 Self-use MVP Demo World Cut
completion and archive. It is documentation-only: no backend behavior, Web behavior,
migrations, API routes, runtime contracts, or provider calls were changed.

## Conclusion

Recommendation: **C. v1.0 phase order must be revised before implementation.**

v0.9 provides the minimum content and operator foundation for private beta: configurable
providers, model lab, visual generation control, already-unpacked galgame intake, script
dialogue extraction, persona/memory distillation, visual/voice mapping, demo assembly,
and a self-use gate. That is enough to begin v1.0 planning, but not enough to safely let
1-3 external testers use the system.

The missing beta foundations are:

- explicit invite/eligibility records or a confirmed membership-only invite model;
- player-owned resume state across worldline, conversation, scene, presentation, and UI route;
- per-player/capability quota enforcement beyond current world/provider daily budgets;
- feedback records or a dedicated beta-feedback layer tied to safe evidence refs;
- a beta readiness gate that extends observability/readiness instead of duplicating it.

Implementation should not start directly from the original order. The first implementation
phase can start only after a docs-only checkpoint confirms the beta access schema/router
decision. The current v1.0 OpenSpec should be revised to front-load access, resume, and
quota before setup wizard and gate work.

## Current Capability Map

### Access, Users, And Membership

Existing support:

- `backend/packages/auth/` provides authenticated users, sessions, and platform roles.
- `WorldMembership` exists with `world_admin` and `human_user` roles.
- `authorization.py` uses deny-by-default behavior for non-members by returning 404 or 403.
- `worlds.py` has admin membership list/upsert/delete and access-review endpoints.
- `PlayerActorProfile` is strict worldline/user scoped and can represent a player identity.

Gaps:

- No invite token, beta eligibility record, invite status, expiration, redemption audit, or
  private beta access package exists.
- `WorldMembership` can admit testers only after admin action and does not distinguish invited,
  accepted, revoked, waitlisted, or beta-limited access.
- Tester onboarding cannot currently create access without an admin already adding a membership.
- Role vocabulary is coarse. `human_user` is not enough by itself to distinguish beta tester,
  reader, player, and member capabilities in UI copy and route policy.

### Provider, Cost, And Quota

Existing support:

- v0.9 provider settings/model lab supports code-owned provider templates, custom `base_url`,
  server-side model discovery, manual model-name fallback, smoke tests, and OpenAI-compatible
  / Anthropic-compatible text execution through `ProviderExecutionService`.
- `ProviderBudgetPolicy` and `ProviderBudgetService` enforce world/provider daily invocation,
  daily estimated cost, daily media job limits, and emergency stop before provider execution.
- Provider execution records budget-block metadata through invocation paths.

Gaps:

- Existing budget policies are world/provider scoped. There is no per-player budget table or
  first-class limit by capability such as `text_generation`, `image_generation`, `tts`, or `asr`.
- Media/image/speech paths need a v1.0 coverage audit to prove every runtime spend path checks
  the same quota boundary before external provider calls.
- There is no tester-facing quota-exceeded UX or degraded-mode contract.

### Sessions, Conversations, And Presentation Restore

Existing support:

- `ConversationSession`, `ConversationTurn`, and `ConversationTurnPresentation` are worldline
  aware and preserve conversation/presentation state.
- Reader playback and scene view render safe presentation media through reader media delivery.
- Conversation sessions can start, pause, resume, stop, and expose turns.

Gaps:

- There is no player-session record with current worldline, current conversation, current scene,
  last presentation, route state, and recovery status.
- Conversation sessions are not player-owned by default; multiple testers could collide unless
  v1.0 adds a player/session association or deterministic per-player session key.
- Resume UX is route/page state, not a server-owned beta resume contract.
- Provider/media failure fallback is present in reader surfaces, but not unified as a player
  session recovery status.

### Feedback, Incidents, And Evidence

Existing support:

- `backend/packages/moderation/` has report/action/incident records with safe evidence refs,
  reviewer lifecycle, and world/worldline scope.
- `IncidentEvidenceRef` provides safe references for readiness and incident reporting.
- Moderation reports can be created by world members and triaged by admins.

Gaps:

- Moderation is heavier than beta feedback and is category/severity oriented. It lacks beta
  issue types such as dialogue, persona, memory, sprite, background, voice, playback, provider,
  and UX issue.
- Current moderation target kinds cover conversation/session/turn/media/player profile, but not
  presentation, invocation, persona, memory, voice profile, visual generation plan, or authoring
  proposal as first-class beta feedback targets.
- There is no tester-facing beta feedback UI or admin beta triage surface.

### Readiness, Gate, And Setup Evidence

Existing support:

- `ProductionReadinessGateService` aggregates internal production readiness, public launch
  readiness, and v0.9 self-use MVP evidence without duplicating readiness tables.
- Existing readiness sections already inspect beta checklist, provider governance, budget
  controls, player privacy, moderation, diagnostics, media, and source traceability.
- v0.9 self-use gate explicitly says self-use evidence does not imply beta readiness.

Gaps:

- No private beta readiness report exists.
- Existing `BetaChecklistRun` is a living-world beta checklist, not the v1.0 private beta gate.
- Setup wizard requirements depend on evidence from onboarding, session stability, quota,
  feedback, and QA; therefore it should not be implemented before those contracts are clear.

### Authoring, Memory, Visual, Voice, And Repair

Existing support:

- v0.9 implemented authoring import/review/apply, dialogue extraction, persona/memory
  distillation, visual mapping, voice mapping, demo assembly, and source traceability.
- Persona output writes through `AgentPersona`; structured character fields use
  `Agent.character_profile`; memory writes use reviewed memory apply paths.
- Visual and voice bindings reuse existing `visual` and `speech` packages.
- `visual_generation` owns workflow templates, model inventory, character visual profiles,
  provider-neutral plans, validators, and dry-run mapping.

Gaps:

- QA is not yet a beta operator workflow for drift, contamination, rollback, and trend evidence.
- Feedback-to-repair proposals are not connected as a v1.0 loop.
- Repair proposal ownership should reuse authoring proposals when mutating content, but beta
  feedback itself may need a lighter dedicated package.

## Phase Findings

### Phase 1 - Private Beta Onboarding

Current capability map:

- Reuse auth users/sessions, world memberships, `PlayerActorProfile`, player UI shell, reader
  scene/playback pages, and world access review.
- Existing membership admin can add a user as `human_user`; player actor binding can create a
  worldline-scoped identity.

Missing capabilities:

- invite token or beta eligibility record;
- invitation status lifecycle;
- onboarding route/API that creates the right membership/profile/identity without admin DB edits;
- first-run guidance and player-safe world selection;
- explicit tester least-privilege policy.

Likely migration needs:

- Recommended: add `private_beta_invites` or `beta_access_grants` unless the checkpoint proves
  `world_memberships` plus metadata is sufficient. The current membership table has no metadata,
  status, expiry, redemption, or inviter audit, so a migration is likely.

Likely package/router ownership:

- Prefer `backend/packages/private_beta/` plus `backend/services/api/src/noveland/services/api/private_beta.py`.
- Auth stays in `auth`; world membership remains access enforcement; `worlds.py` should not grow
  broad onboarding routes.

Frontend needs:

- Invite redemption/onboarding flow, player profile/identity setup, world selection, and first-run
  guidance. `impeccable` is required before implementation.

Tests needed:

- uninvited denial, expired/revoked invite denial, invite redemption, membership/profile creation,
  repeated redemption idempotency, least-privilege route access, no provider/admin/media/invocation
  leaks, and safe first-run copy.

Stop conditions:

- public signup becomes necessary;
- onboarding requires admin/provider privileges for testers;
- membership-only model cannot represent revoke/expiry/redemption safely;
- any player response exposes provider configuration, diagnostics, storage paths, raw prompts,
  raw outputs, prompt snapshot internals, or secrets.

Can start as-is?

- No. Start with a Phase 1 checkpoint deciding invite schema/router ownership and whether
  `WorldMembership` alone is sufficient.

### Phase 2 - World Setup Wizard

Current capability map:

- Reuse provider health/model discovery/smoke, `visual_generation`, authoring source/proposals,
  visual/speech bindings, self-use gate, moderation, player privacy, budget controls, and
  observability readiness sections.

Missing capabilities:

- private beta readiness report;
- setup checklist that depends on invite/onboarding, session stability, quota, feedback, and QA;
- beta-world publish/eligibility status for tester entry.

Likely migration needs:

- Avoid a duplicate setup table initially. Use read-only observability aggregation unless a
  persistent beta world status/signoff record is approved.

Likely package/router ownership:

- `observability` should own readiness report aggregation.
- If a wizard needs operator actions, use a narrow `private_beta` setup endpoint; do not put a
  broad wizard into `worlds.py`.

Frontend needs:

- Admin setup checklist/readiness UI. `impeccable` required before implementation.

Tests needed:

- complete world passes, missing provider/model/persona/memory/visual/voice blocks, self-use
  gate evidence referenced safely, player requests denied or redacted, no raw prompts/outputs or
  storage paths in report.

Stop conditions:

- setup duplicates readiness framework;
- setup requires raw prompt/output, storage path, or provider secret evidence;
- setup is implemented before session/quota/feedback evidence can be represented.

Can start as-is?

- No. Move after access, session, and quota foundations so the wizard can validate the actual
  private beta path.

### Phase 3 - Player Session Stability

Current capability map:

- Reuse conversation sessions/turns, turn presentations, reader media descriptors, scene view,
  player actor profile, player choices/interventions/journal, and worldline isolation.

Missing capabilities:

- player-owned session record;
- current worldline/conversation/scene/presentation pointer;
- resume endpoint;
- route-state restoration;
- provider/media job failure state contract;
- multiple tester isolation for the same world.

Likely migration needs:

- Likely add `player_sessions` or `private_beta_player_sessions` with `world_id`,
  `worldline_id`, `user_id`, `player_actor_id`, `conversation_id`, `scene_id`,
  `last_turn_id`, `last_presentation_id`, `status`, safe `resume_state`, and timestamps.

Likely package/router ownership:

- Prefer `backend/packages/player_sessions/` or `private_beta` session ownership with a dedicated
  router. Conversation mechanics remain in `conversations`; presentations remain in
  `conversation_presentations`.

Frontend needs:

- Resume landing/restore flow, player-safe loading/error/fallback states, and scene/playback
  state persistence. `impeccable` required before implementation.

Tests needed:

- close/reopen resume, cross-player isolation, cross-world/worldline rejection, stale
  conversation fallback, missing media fallback, provider failure fallback, no raw event payload
  exposure, no storage/path/base64/bytes leaks.

Stop conditions:

- resume requires exposing raw event payloads or admin-only diagnostics;
- session state conflicts with worldline isolation;
- multiple testers share the same conversation/session unintentionally.

Can start as-is?

- No. It needs a schema/API checkpoint and should move before setup wizard.

### Phase 4 - Memory & Persona QA

Current capability map:

- Reuse `AgentPersona`, `Agent.character_profile`, memory records, authoring source traceability,
  narrative quality diagnostics, invocation ledger safe refs, and v0.9 distillation proposals.

Missing capabilities:

- admin-facing QA runs for persona drift, memory contamination, style drift, relationship drift,
  source coverage, and worldline contamination;
- baseline and comparison policy;
- repair proposal linkage.

Likely migration needs:

- Start read-only if possible by using narrative quality eval runs/findings and authoring
  proposals. A persisted `memory_persona_qa_runs` table may be useful only if diagnostics need
  lifecycle/triage distinct from existing eval records.

Likely package/router ownership:

- `narrative_quality` or a narrow memory/persona diagnostics service should own QA evidence.
- `authoring` owns repair proposals and apply.

Frontend needs:

- Admin QA diagnostics and repair proposal review. `impeccable` required if Web is included.

Tests needed:

- drift/contamination fixture, source traceability refs, cross-worldline rejection, redaction,
  proposal-only repair, no direct memory/persona mutation.

Stop conditions:

- QA needs raw prompts/outputs in non-admin responses;
- repair bypasses authoring review/apply;
- initial memory cannot be shown to enter agent context through safe evidence.

Can start as-is?

- Needs checkpoint, but can remain mid-sequence after session/quota foundations.

### Phase 5 - Beta Feedback System

Current capability map:

- Reuse moderation report/action/incident workflow, `IncidentEvidenceRef`, conversation
  presentations, reader media, invocation safe refs, player actor/profile, and authoring proposals.

Missing capabilities:

- beta issue taxonomy;
- contextual feedback target refs for presentation, invocation, persona, memory, visual/voice
  binding, provider failure, and UX;
- feedback attachment policy;
- tester feedback UI and admin triage UI;
- feedback-to-repair proposal bridge.

Likely migration needs:

- Decision needed. Extending moderation is feasible but semantically heavy. A dedicated
  `beta_feedback_reports` table with safe refs and optional links to moderation incidents is
  likely cleaner for beta usability.

Likely package/router ownership:

- Prefer `backend/packages/beta_feedback/` and `beta_feedback.py` for beta issue workflow.
- Moderation remains for safety/abuse/incidents and can be linked when feedback escalates.

Frontend needs:

- Inline tester feedback on scene/playback/player surfaces and admin triage. `impeccable`
  required before implementation.

Tests needed:

- feedback create/list/triage, reporter privacy, evidence ref validation, cross-world/worldline
  rejection, attachment redaction, links to repair proposals, no raw prompt/output/storage/secret
  leaks.

Stop conditions:

- feedback becomes a public forum/social feature;
- feedback evidence requires raw prompts, prompt snapshots, storage paths, bytes, or secrets;
- reporter private data is visible to other testers.

Can start as-is?

- No. Needs a package/schema ownership checkpoint.

### Phase 6 - Cost & Quota Real Enforcement

Current capability map:

- Reuse `ProviderBudgetPolicy`, `ProviderBudgetService`, provider execution pre-call checks,
  provider quota status, media jobs, model invocations, and emergency stop.

Missing capabilities:

- per-player quota;
- per-capability quota;
- image/TTS/ASR/LLM-specific fallback/degraded UX;
- provider execution coverage audit across runtime, speech, visual generation, asset generation,
  and model lab smoke paths;
- admin override audit by tester/player.

Likely migration needs:

- Either extend `provider_budget_policies.limits` with a documented player/capability policy
  plus a player usage aggregation source, or add a `provider_quota_overrides` /
  `player_quota_policies` table. Current schema cannot persist player-scoped policies cleanly.

Likely package/router ownership:

- Stay in `providers` for provider spend enforcement. Add private beta/player quota helpers only
  if the provider package remains the pre-call guard source.

Frontend needs:

- Admin quota controls and tester quota-exceeded/degraded states. `impeccable` required if Web
  is included.

Tests needed:

- world/provider/player/capability limit blocks, emergency stop, safe fallback response,
  explicit override audit, no hidden spend, no real provider calls by default, full path coverage
  for text/image/TTS/ASR.

Stop conditions:

- any runtime provider call bypasses quota;
- quota failure is silent or retries into hidden spend;
- per-player enforcement cannot identify the current tester.

Can start as-is?

- Needs a checkpoint and should move before setup wizard so readiness can validate cost safety.

### Phase 7 - Beta Content Iteration Loop

Current capability map:

- Reuse authoring proposals/review/apply, v0.9 persona/memory/visual/voice mapping apply paths,
  narrative quality diagnostics, visual/speech bindings, and feedback evidence refs.

Missing capabilities:

- beta repair proposal kinds linking feedback to persona, memory, dialogue style, sprite/voice,
  background, script extraction, provider prompt/profile, and visual generation profile fixes;
- rollback/readability evidence for applied repairs;
- repair impact report.

Likely migration needs:

- Avoid initially by using authoring proposal payloads and safe refs. Add dedicated repair tables
  only if authoring proposals cannot represent feedback linkage and lifecycle.

Likely package/router ownership:

- `authoring` owns repair proposals and apply. `beta_feedback` owns feedback lifecycle.
  `visual_generation`, `visual`, `speech`, `memory`, and `agents` remain applied target owners.

Frontend needs:

- Admin repair review/apply UI. `impeccable` required if Web is included.

Tests needed:

- OOC repair proposal, memory repair, sprite/voice/background repair, provider/profile repair,
  worldline isolation, audit/source/feedback traceability, no direct mutation before review.

Stop conditions:

- feedback automatically mutates world state;
- repairs bypass authoring review/apply;
- applied repair loses source or feedback traceability.

Can start as-is?

- Needs feedback and QA foundations first.

### Phase 8 - Private Beta Gate

Current capability map:

- Reuse observability readiness reports, v0.9 self-use gate, production/public launch gate
  patterns, provider quota status, moderation/feedback evidence, session evidence, and no-leak
  checks.

Missing capabilities:

- private beta readiness report over 1-3 tester evidence;
- 1-2 hour manual test checklist/evidence;
- explicit non-public-launch readiness distinction;
- gate failure criteria for onboarding, session resume, quota, feedback, QA, and content repair.

Likely migration needs:

- Prefer no migration. Implement as read-only observability aggregation unless an explicit
  signoff record is approved.

Likely package/router ownership:

- `observability` owns the gate. Do not duplicate release frameworks or put it in `worlds.py`.

Frontend needs:

- Admin readiness/gate report. `impeccable` required if Web is included.

Tests needed:

- pass with complete evidence, fail without quota/session/feedback/QA, leak fixture, admin-only
  ACL, distinction from public launch readiness.

Stop conditions:

- gate duplicates readiness framework;
- gate implies public launch readiness;
- gate needs raw prompt/output/storage path or secret evidence.

Can start as-is?

- No. Gate depends on the previous evidence-producing phases.

## Recommended Revised Phase Order

1. Private Beta Onboarding & Access Model
2. Player Session Stability
3. Cost & Quota Real Enforcement
4. World Setup Wizard
5. Memory & Persona QA
6. Beta Feedback System
7. Beta Content Iteration Loop
8. Private Beta Gate

Rationale:

- Access must come first because every other private beta path depends on deny-by-default tester
  eligibility and least-privilege membership semantics.
- Session stability should precede setup wizard because the wizard must validate real resume
  evidence, not just static content readiness.
- Quota enforcement should precede setup wizard because external testers should not enter before
  spend is bounded.
- Setup wizard then aggregates concrete onboarding, session, quota, provider, media, memory,
  visual, voice, and self-use evidence.
- QA, feedback, and repair form the beta operations loop.
- The private beta gate comes last as an extension of observability/readiness.

## Migration Expectations

Likely migrations:

- private beta invite/access records;
- player session/resume records;
- beta feedback records, unless moderation is explicitly extended;
- player/capability quota policy or override records if JSON-only provider policy extension is
  insufficient.

Likely no migration:

- world setup wizard if implemented as read-only observability aggregation;
- memory/persona QA if implemented through existing eval/diagnostics and authoring proposals;
- beta content iteration if authoring proposals can carry feedback/evidence refs;
- private beta gate if implemented as read-only observability aggregation.

## Package / Router Recommendations

- Add `backend/packages/private_beta/` and `private_beta.py` only if invite/access/onboarding
  needs a dedicated boundary. This is the preferred path if migrations are needed.
- Add `backend/packages/player_sessions/` only if session/resume ownership becomes too large for
  `private_beta`. Otherwise keep a narrow player-session submodule inside `private_beta`.
- Add `backend/packages/beta_feedback/` and `beta_feedback.py` if moderation cannot cleanly
  represent beta issue taxonomy, feedback privacy, and repair links.
- Keep quota enforcement in `backend/packages/providers/` so `ProviderExecutionService` remains
  the spend guard.
- Keep setup wizard and private beta gate under `backend/packages/observability/` as derived
  reports.
- Keep repair apply under `backend/packages/authoring/`.
- Do not add broad routes to `worlds.py`.

## Provider Adapter Gaps

- Provider adapters are sufficient for v1.0 feasibility, but quota coverage must be proven across
  text, image, TTS, ASR, visual generation dry-run/execution boundaries, asset generation, and
  model lab smoke paths.
- No real provider tests should run by default; keep the v0.9 provider lab opt-in convention.
- Quota failure and provider failure must produce safe player-facing fallback states, not raw
  provider errors or hidden retries.

## Frontend Gaps

v1.0 will touch Web unless explicitly implemented API-first only:

- invite redemption/onboarding;
- player identity/world selection;
- resume/restore states;
- quota exceeded/degraded states;
- admin setup wizard;
- memory/persona QA;
- tester feedback and admin triage;
- repair review/apply;
- private beta gate report.

`impeccable` is required before any Web implementation phase. The UI should remain operational
and task-focused: no landing-page flow, no vague AI-demo copy, no hidden provider spend, and no
admin diagnostics in tester surfaces.

## Risks And Stop Conditions

Stop v1.0 implementation if any of these occurs:

- beta access cannot be deny-by-default and least-privilege;
- invite/onboarding cannot be represented without public signup;
- player session recovery cannot preserve world/worldline/player isolation;
- multiple testers share mutable session state unintentionally;
- per-player/provider/capability quota cannot block before provider execution;
- feedback evidence requires raw prompt/output, prompt snapshot internals, storage paths, bytes,
  base64, or secrets;
- beta content fixes bypass authoring preview/review/apply;
- private beta readiness duplicates observability/readiness or implies public launch readiness;
- implementation requires broad `worlds.py` route growth;
- Web UI is required but `impeccable` cannot be read and used first.

## Required Decisions Before Implementation

1. Invitation model: dedicated invite/access table vs membership-only with a documented reason.
2. Player session schema: dedicated `player_sessions` boundary vs private-beta submodule.
3. Feedback ownership: extend moderation or add dedicated beta feedback records.
4. Quota model: JSON policy extension vs player/capability quota tables.
5. Setup/gate ownership: observability aggregation with optional signoff, not a new readiness
   framework.
6. Web scope per phase and `impeccable` usage before implementation.

## Implementation Recommendation

Do not start v1.0 implementation as-is. Revise the OpenSpec order and task list first, then begin
Phase 1 with a docs-only checkpoint for invite/access ownership. After that checkpoint is accepted,
v1.0 can proceed phase by phase without re-evaluating the whole milestone.
