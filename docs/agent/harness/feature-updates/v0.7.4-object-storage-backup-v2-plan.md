# v0.7.4 Object Storage & Backup v2 Plan

## Goal

Add a safe, repeatable storage integrity and backup/restore verification layer for the existing local object storage and media object storage systems.

This phase is backend/service/test/docs focused. It should prove media objects and snapshot payloads exist, match recorded size/checksum metadata where applicable, and can be verified without exposing filesystem paths, raw bytes, base64, raw prompts, or raw outputs.

## Scope

- Add a read-only storage integrity audit service for:
  - `media_objects`
  - current media object payload bytes
  - object-storage-backed `world_snapshots.payload_uri`
  - local object storage root readiness
- Return safe findings with record IDs, status codes, counts, and mismatch reasons.
- Avoid returning raw `storage_uri` values, raw filesystem paths, object bytes, base64, raw snapshot payloads, raw prompts, or raw outputs.
- Add an operator verification entrypoint or extend the existing `noveland-backup-verify` path if the implementation can stay small.
- Update `docs/agent/operations/backup-restore.md` with v0.7 preflight, backup, restore, and post-restore verification guidance.
- Keep remote S3/GCS-compatible storage as a future abstraction target only; do not implement a cloud provider in this phase.
- Add focused tests for missing media object, size mismatch, checksum mismatch, snapshot payload missing/unreadable, safe output redaction, and backup verification behavior.

## Non-goals

- No public media CDN or public reader delivery.
- No destructive restore API or Web UI.
- No managed-cloud lock-in.
- No S3/GCS provider implementation in this phase.
- No migration unless implementation proves existing tables cannot express audit evidence.
- No bulk historical backfill.
- No broad `worlds.py` route growth.
- No raw storage path, raw byte, base64, raw prompt, or raw output exposure.

## Architecture Decision

Use the existing storage and media boundaries:

- Put storage verification code in `backend/packages/storage/` unless a small media-specific helper is more natural.
- Reuse `LocalObjectStorage` for `object://...` snapshot payload checks.
- Reuse `LocalMediaObjectStorage` / `MediaObjectStorage` for `media://...` media object checks.
- Reuse `media_objects`, `media_assets`, and `world_snapshots`; do not create a duplicate storage inventory table.
- If an API endpoint is needed, add a platform-admin read-only operational route under the existing runtime/operations surface, not `worlds.py`.

Rationale: v0.7 Phase 4 is operational hardening for existing storage records. The system already has a storage package, media storage facade, snapshot payload storage, runtime operator routes, and backup verification command. A new storage framework or provider is unnecessary for this phase.

## Expected Migration

No migration is expected.

Stop if implementation requires:

- persisted audit-run tables
- object schema normalization
- media object backfill
- new public storage references

## Deliverables

- Storage integrity audit contracts/service or equivalent focused helper.
- Backup verification update if needed.
- Optional platform-admin read-only API for safe storage audit summaries if it fits the existing runtime operations boundary.
- Updated backup/restore playbook.
- Focused tests for media object integrity, snapshot payload integrity, safe output, and backup verification.
- Updated OpenSpec Phase 4 task status and harness docs after implementation.

## Guardrails

- Audit output must use safe IDs, counts, status codes, and reasons.
- Audit output must not include raw `storage_uri`, filesystem paths, bytes, base64, raw prompts, or raw outputs.
- Snapshot payload checks may verify readability but must not return payload content.
- Media checks may read bytes internally to compute checksum but must not return bytes or base64.
- Lower-privilege/member/reader/player APIs must not gain any storage audit surface.
- Backup/restore remains an operator procedure, not a destructive API.

## Stop Conditions

- A cloud storage SDK/provider becomes necessary for acceptance.
- Audit output requires exposing raw storage paths, raw `storage_uri`, object bytes, base64, raw prompts, or raw outputs.
- The phase needs broad new `worlds.py` routes.
- A migration is needed for audit evidence persistence or object schema changes.
- Backup verification would perform destructive restore actions.
- Targeted tests or the full local gate fail.

## Targeted Tests

- Local media audit passes for existing object with matching size and checksum.
- Media audit detects missing object.
- Media audit detects size mismatch.
- Media audit detects checksum mismatch.
- Snapshot audit detects missing/unreadable object payload.
- Audit output excludes raw `storage_uri`, filesystem paths, bytes, base64, raw prompts, and raw outputs.
- Backup verification reports object root and snapshot payload readiness.
- Optional runtime API is platform-admin only and returns safe audit summaries.
- Existing media storage traversal rejection tests remain passing.
