# v0.7 Production Hardening Feasibility Review

Date: 2026-05-15

## Current Baseline

- v0.4 Operator/Admin UX is implemented and archived in OpenSpec.
- v0.5 Authoring & Import Studio is implemented and archived in OpenSpec.
- v0.6 Runtime Narrative Quality is locally complete: all 105 OpenSpec tasks are done, Phase 10 is fast-forward merged, and the full local gate passed.
- v0.6 is ready to archive, but this review does not archive it.
- Current `main` is local-ahead of `origin/main`; do not push unless explicitly requested.

## Feasibility Summary

v0.7 is feasible as a hardening release, but the original OpenSpec skeleton was too generic and predated the completed v0.6 narrative quality APIs. The plan now needs to account for the expanded admin-only API surface and the existing package/router boundaries.

Primary planning adjustments:

- Treat v0.7 as API/test/docs-first unless a later phase explicitly accepts Web work.
- Start with permission matrix and ACL regression baseline before provider/cost/deployment work.
- Keep provider governance tied to `ProviderSecretResolver`, provider status, provider health, and invocation ledger evidence.
- Apply cost/rate controls at execution boundaries before external calls.
- Reuse `storage`, `media`, `observability`, `multimodal_eval`, `narrative_quality`, `auth`, and `providers` packages instead of creating duplicate systems.
- Avoid broad new `worlds.py` routes. Stop for a dedicated production-hardening package/router decision if cross-cutting APIs cannot fit existing boundaries.

## Revised v0.7 Order

1. **Permission Matrix & ACL Regression Baseline**
   - Document route matrix across platform-admin, world-admin, world-member, reader, and player surfaces.
   - Add lower-privilege leak regression tests.
   - Fix only matrix conflicts discovered during the phase.

2. **Secret & Provider Governance**
   - Harden provider disable/rotation/audit.
   - Keep `auth_ref` opaque and resolved only in memory.
   - Confirm disabled providers block image, speech, smoke, provider, and narrative quality execution paths.

3. **Cost & Rate Control**
   - Add budget/quota status and pre-call budget blocks.
   - Cover provider execution, media jobs, asset generation, and provider-backed narrative quality generation.

4. **Object Storage & Backup v2**
   - Audit media object and snapshot integrity.
   - Improve local backup/restore drills.
   - Keep remote storage abstract and optional.

5. **Deployment Profile**
   - Define local/single-host production-like profile, health checks, migration procedure, and rollback prerequisites.

6. **Observability & Incident Diagnostics**
   - Aggregate safe provider/media/runtime/eval/cost/narrative quality incident evidence.
   - Reuse `noveland.observability` and existing diagnostics.

7. **Security Regression Suite**
   - Consolidate secret, prompt/output, storage/path, ACL, and worldline isolation regressions after earlier v0.7 hardening phases.

8. **Production Readiness Gate**
   - Aggregate v0.7 evidence into an internal readiness gate.
   - Reuse beta/release/eval/diagnostics evidence; do not create a duplicate release system.

## Phase-Specific Migration Expectations

- Phase 1 should be no-migration unless the existing platform/world membership model cannot express the accepted matrix.
- Phase 2 should first reuse provider status, health checks, and model invocation metadata. A provider audit table requires an explicit migration plan.
- Phase 3 likely needs persisted budget policy unless existing asset generation policies can cover the accepted first scope.
- Phase 4 should avoid schema changes unless media object/snapshot storage references require new metadata.
- Phase 5 should be mostly docs/config/tests.
- Phase 6 should reuse `runtime_diagnostic_events` and existing eval/ledger records where possible.
- Phase 7 should be test/fixture-heavy and should not need migrations.
- Phase 8 should reuse `BetaChecklistRun`, `LongRunEvalRun`, release profiles, multimodal evals, and narrative quality summaries before proposing new tables.

## Deferred Items

- Public launch readiness.
- Web dashboard work unless a later phase accepts it.
- Provider marketplace.
- Full vault/KMS or encrypted DB secret storage.
- External observability exporter.
- Kubernetes/autoscaling/cloud-provider lock-in.
- Streaming.
- Automatic provider fallback/load balancing.

## Stop Conditions

Stop before implementation if any phase requires:

- broad new `worlds.py` routes;
- unresolved production-hardening package/router boundary;
- storing resolved provider secrets;
- exposing raw prompts, raw outputs, storage paths, bytes, base64, or prompt snapshots to member/reader/player routes;
- new schema not covered by that phase plan;
- runtime daemon automation, public reader delivery, or provider marketplace scope;
- failing targeted tests or full local gate.

## Open Architecture Decisions

- Whether cross-cutting readiness APIs should use a new `production_hardening` package/router or stay inside existing bounded routers only.
- Whether provider audit needs a new table or can reuse provider health plus invocation ledger metadata for v0.7 first scope.
- Whether cost/rate control should introduce a new policy table or reuse existing asset generation/provider config in the first phase.
- Whether Web admin status surfaces should be deferred entirely until backend hardening APIs stabilize.
