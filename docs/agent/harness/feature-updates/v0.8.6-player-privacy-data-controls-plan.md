# v0.8.6 Player Privacy & Data Controls Plan

Date: 2026-05-16
Branch: `main`

## Scope

Implement authenticated player privacy workflows that let a player request a safe data export and create reviewable deletion/redaction requests without automatically deleting shared canonical world history.

## Accepted Design

- Add a narrow player privacy boundary rather than broad new `worlds.py` routes.
- Export only player-owned or player-visible records: profile/membership summary, eligible choices, journal entries, notifications, interventions, and safe conversation references.
- Represent deletion as a reviewable privacy request with a redaction plan when requested records are part of shared world state.
- Keep all destructive actions out of Phase 6. Admin review may update request status and safe review notes, but must not delete shared world, media, provider, conversation, or event records.
- Store only safe request metadata, actor refs, status, and counts/evidence refs. Do not store raw prompt/output, object storage paths, bytes, base64, resolved secrets, or raw event payloads.
- Add a player-facing Web workflow if needed for export/delete requests, using existing authenticated workspace and product UI patterns.

## Non-Goals

- No automatic deletion of shared canonical world history.
- No legal compliance automation beyond product-level export and request tracking.
- No public unauthenticated privacy controls.
- No deletion of shared world/media/provider records.
- No admin-only diagnostic, prompt snapshot, or invocation detail export.
- No raw storage URI, filesystem path, base64, bytes, raw prompt, raw output, resolved secret, or raw world event payload exposure.

## Current Capability Inventory

- Phase 3 Player Interaction UI already exposes player choices, interventions, journals, and notifications through authenticated player/member workflows.
- Existing world membership and auth dependencies distinguish current-user, world-member, and admin contexts.
- Existing conversation playback and scene views provide reader/player-safe conversation references without exposing admin evidence.
- Existing v0.7 security regression and v0.8 reader media patterns provide leak tests for storage paths, raw prompts, bytes/base64, and secrets.

## Implementation Notes

- Prefer a dedicated backend package/router if persistent privacy request records are required. Keep routes outside `worlds.py`.
- If a migration is required, scope it to privacy request/export metadata only and document the schema in the implementation commit.
- Keep export generation deterministic and local. It should aggregate existing records and return sanitized JSON, not enqueue background jobs or provider calls.
- Model deletion as `requested`, `under_review`, `approved_for_redaction`, `rejected`, or similar safe states. Phase 6 may record intent and review outcome, but must not perform destructive redaction unless OpenSpec is updated first.
- Reuse existing player records and authorization checks; do not invent replacement player state.
- UI should be quiet and task-focused: export summary, request form, status list, and shared-world safeguard copy.

## Targeted Validation

- Backend tests for player export ACL, own-data filtering, shared-world safeguards, review request lifecycle, and no-leak payloads.
- Web component/e2e tests if a player-facing privacy page is added.
- OpenSpec strict validation and `git diff --check`.
- Full local gate after implementation.
