# v0.8.3 Player Interaction UI Plan

Date: 2026-05-16
Branch: `main`

## Scope

Implement the first authenticated player/member interaction surface using the existing player records: choices, interventions, journal entries, notifications, route affinity summaries, and route milestones. This phase is primarily Web-focused, with only narrow backend ACL adjustment allowed if needed to expose existing player choice records to the owning player.

## Accepted Design

- Add a player-facing route under the world workspace, separate from admin diagnostics and authoring controls.
- Reuse existing `PlayerChoiceRecord`, `PlayerJournalEntry`, `InWorldNotification`, and `PlayerInterventionRecord` APIs and DTOs.
- Reuse existing route affinity and route milestone records only for safe feedback summaries.
- Keep player actions worldline-aware.
- Filter player-owned journal, notifications, choices, and interventions to the current authenticated user unless the caller is a world admin.
- Allow player/member intervention submission through the existing intervention endpoint.
- Adjust existing player choice list/record/preview endpoints narrowly if needed so members can access and submit only their own choices.
- Do not add a replacement player state model or new player record framework.

## Non-Goals

- No backend migration.
- No provider execution.
- No direct canonical world-state mutation outside existing player choice/intervention record paths.
- No admin diagnostics, prompt snapshots, raw provider outputs, or hidden route evidence in player UI.
- No raw prompt/output, storage URI, filesystem path, base64, bytes, or resolved secret exposure.
- No public unauthenticated access.
- No broad new `worlds.py` routes.
- No Web UI for moderation, privacy controls, world packaging, plugin marketplace, or launch gate in this phase.

## Current Capability Inventory

- `GET /worlds/{world_id}/player-journal` is member-readable and filters to the current user unless caller is world admin.
- `GET /worlds/{world_id}/notifications` is member-readable and filters to the current user unless caller is world admin.
- `GET/POST /worlds/{world_id}/interventions` is member-readable/member-submittable with current-user enforcement.
- `GET/POST /worlds/{world_id}/player-choices` and `POST /worlds/{world_id}/player-choices/preview` currently use admin context and need a narrow ACL adjustment for player-facing use.
- `GET /worlds/{world_id}/route-affinities` and `GET /worlds/{world_id}/route-milestones` are admin-scoped; Phase 3 UI may show safe route feedback only from existing records already available to the player-facing loader or from sanitized summaries.

## Implementation Notes

- Prefer a route such as `/worlds/{world_id}/player` for player/member interaction.
- Use existing same-origin world proxy routes and CSRF-aware client helpers.
- Add a small feature component rather than expanding the existing large overview page.
- Keep UI copy practical and task-focused: choices, interventions, journal, and notifications.
- Provide deterministic empty states for worlds with no choices, no journal entries, no notifications, or no interventions.
- Keep route feedback spoiler-safe by showing high-level status labels and counts, not hidden future milestone evidence.
- Reject or omit hidden/admin-only evidence fields in tests.

## Targeted Validation

- Web component tests for rendering choices, journal, notifications, interventions, safe route feedback, and empty states.
- Web client tests for any changed player helper behavior.
- Backend API/ACL tests only if existing player choice ACL is adjusted.
- E2E smoke proving an authenticated member can open the player surface, see owned player records, submit an allowed intervention, and avoid hidden/admin-only leak markers.
- Full local gate after implementation.
