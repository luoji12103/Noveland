# v1.1 Normal Use / Release Candidate Feasibility Review

## Scope

This review evaluates the active OpenSpec change `openspec/changes/v1-1-normal-use-release-candidate/` after v0.9 Self-use MVP Demo World Cut and v1.0 Private Beta MVP completion and archive. It is documentation-only: no backend behavior, Web behavior, migrations, API routes, runtime contracts, or provider calls were changed.

The review treats v1.1 as normal-use hardening and release-candidate preparation, not as a general feature expansion after private beta.

## Conclusion

Recommendation: **B. v1.1 can start after minor OpenSpec adjustments.**

The current phase order is directionally correct:

1. Operational Runbooks
2. Real Backup/Restore Drill
3. Multi-world / Multi-user Stress Test
4. Content Safety & Moderation Hardening
5. Import/Export Stability
6. Provider Reliability Layer
7. User-facing Polish
8. Release Candidate Gate

The order should not be revised before implementation. v1.1 can start after this feasibility review updates the active OpenSpec with explicit checkpoint decisions for:

- fresh local/single-host restore drill target;
- first multi-world/multi-user stress baseline;
- manual-first provider reliability policy with opt-in fallback;
- expanded operational runbook list;
- user-facing polish scope and `impeccable` requirement;
- release-candidate gate as an extension of existing observability/readiness, not a duplicate gate framework.

Implementation should still begin each phase with a docs-only checkpoint because several phases touch operational evidence, restore drill mechanics, stress fixtures, provider retry/fallback policy, or UI scope.

## Feasibility Answers

### 1. Can current main support v1.1 implementation?

Yes, with checkpoint discipline. Current `main` has the major foundations v1.1 needs:

- v0.7 production hardening, permission, secret governance, cost controls, backup docs, deployment docs, and readiness gates.
- v0.8 public/player surfaces, reader-safe media, packaging, moderation/incident workflow, privacy controls, and public launch gate.
- v0.9 provider lab, visual generation control plane, galgame intake, persona/memory distillation, visual/voice mapping, demo assembly, and self-use MVP gate.
- v1.0 invite-only private beta access, player sessions, quota enforcement, setup readiness, memory/persona QA, beta feedback, repair proposal bridge, and private beta gate.

The gaps are not blockers to planning. They are exactly the v1.1 work: operational drills, stress evidence, stronger safety regression, safer repeatable import/export, provider reliability behavior, UI polish, and RC evidence aggregation.

### 2. Is the v1.1 phase order reasonable?

Yes. Runbooks should come first because they expose missing operational controls. Backup/restore should come before stress and RC gate because normal use cannot be considered recoverable without a real restore drill. Stress should happen before safety, packaging, provider reliability, and polish gate work because it exposes isolation and recovery gaps. RC gate should remain last.

### 3. Which phases can start directly?

Phase 1 can start after this review is accepted. It is mostly docs/runbooks and should not need a migration or new API routes.

All later phases need a docs-only checkpoint before implementation:

- Phase 2 needs restore target and drill evidence shape.
- Phase 3 needs deterministic stress baseline and fixture ownership.
- Phase 4 needs moderation/beta feedback/privacy integration decision.
- Phase 5 needs package manifest and proprietary asset export policy.
- Phase 6 needs provider retry/fallback ownership and migration decision.
- Phase 7 needs approved UI polish scope and `impeccable` workflow.
- Phase 8 needs RC evidence ownership and gate distinction.

### 4. Where are migration/schema/API decisions likely?

- Phase 1: no migration expected. Docs consistency tests may be enough.
- Phase 2: likely no migration if backup/restore drill evidence can be response-only or file/report based. A persisted drill report should reuse observability/readiness patterns unless a checkpoint approves a table.
- Phase 3: likely no migration for deterministic stress fixtures if tests create transient data. Persisted stress runs should reuse existing eval/readiness records first.
- Phase 4: no new moderation framework. A small migration may be needed only if current moderation/beta feedback tables cannot express safety action traceability.
- Phase 5: avoid new packaging tables. Extend `world_packaging` manifests first.
- Phase 6: possible migration if manual retry/requeue or provider health trends need durable records beyond invocation ledger, provider health, and media job state.
- Phase 7: Web-only or narrow API polish should avoid schema changes unless the checkpoint finds a missing safe DTO.
- Phase 8: avoid new RC gate tables. Add an observability/readiness report unless a checkpoint proves persistence is required.

### 5. Which user paths are still missing?

- Normal-use operator path for provider outage, quota exhaustion, media job stuck, migration failure, restore, rollback, worldline recovery, secret rotation, invite/session/feedback incident, and import/export recovery.
- Admin path to prove a real restore drill in a fresh environment.
- Admin path to run safe multi-world/multi-user stress and inspect results.
- Player-safe degraded mode and quota/provider failure messaging across onboarding, resume, playback, scene view, and feedback.
- Admin path to retry/requeue provider-backed work without hidden spend.
- Admin path to evaluate RC readiness without conflating it with private beta, public launch, or self-use gates.

### 6. Are there risks that block v1.1?

No hard blockers. Main risks are controllable by checkpoint:

- Backup restore may be environment-specific. v1.1 should start with a fresh local/single-host restore target and document staging as later optional scope.
- Stress tests can become quota-consuming. Default stress must use fake/mocked providers; real-provider stress stays opt-in.
- Provider fallback can hide quality or spend problems. v1.1 should be manual-first, with constrained automatic fallback only if a later checkpoint approves policy, audit, capability, and quota checks.
- User-facing polish can sprawl. Phase 7 needs a scoped list of blocking flows and `impeccable` before any Web edits.

Reusable packages/services/routes/tables:

- `backend/packages/observability/`
- `noveland.services.api.observability`
- `noveland.services.api.runtime`
- provider, media, memory, moderation, private beta, player session, feedback, and world packaging docs and APIs as referenced controls

Missing capabilities:

- Runbooks for provider outage, quota exhaustion, media job stuck, migration failure, backup/restore drill, rollback, worldline restore, secret rotation, invite/session/feedback incident, import/export recovery, and provider lab incident evidence.
- Consistency check that referenced critical commands/docs/routes still exist.

Likely migration needs:

- None.

Likely package/router ownership:

- Docs under `docs/agent/operations/`.
- Optional docs consistency tests under backend tests or a docs test helper. No runtime package ownership expected.

Frontend needs:

- None for Phase 1.

Impeccable required:

- No, unless Phase 1 unexpectedly edits Web UI.

Tests needed:

- Forbidden example checks for secrets, storage paths, raw prompts, raw outputs, bytes, and base64.
- OpenSpec and diff checks.

Stop conditions:

- A runbook depends on unimplemented controls without marking the gap.
- Secret rotation guidance exposes real or example secrets.
- Rollback/restore instructions encourage unsafe direct DB mutation as the default path.

Can start as-is?

- Yes, after this feasibility review. The Phase 1 checkpoint can be lightweight and should confirm the final runbook list and docs consistency strategy.

### Phase 2 - Real Backup/Restore Drill

Current capability map:

- `docs/agent/operations/backup-restore.md` documents database dump, object storage archive, migration head, backup verification, and storage audit.
- Storage/media systems track object IDs, checksums, sizes, and safe mismatch reasons.
- Observability/readiness can aggregate safe reports.
- Provider configs use `auth_ref` and secret resolution boundaries.

Reusable packages/services/routes/tables:

- `backend/packages/storage/`
- `backend/packages/media/`
- `backend/packages/worlds/`
- `backend/packages/conversations/`
- `backend/packages/memory/`
- `backend/packages/providers/`
- `backend/packages/observability/`
- `noveland.services.api.runtime` storage audit
- `noveland.services.api.observability`
- Alembic migrations and backup verification CLI

Missing capabilities:

- Executed restore drill against a fresh local/single-host target.
- Safe restore drill report that verifies database, media payloads, checksums, worldlines, conversations, presentations, memory, provider config without secrets, and OpenSpec/docs provenance.
- Clear failure taxonomy for missing media, checksum mismatch, migration mismatch, and provider secret absence.

Likely migration needs:

- Avoid by default. Use an admin-only observability/readiness report or generated artifact. Persist drill runs only if checkpoint proves file/report evidence is insufficient.

Likely package/router ownership:

- `backend/packages/observability/` for drill report aggregation.
- `backend/packages/storage/` and `backend/packages/media/` for verification helpers.
- Existing runtime storage audit can remain the operator entrypoint unless a dedicated admin endpoint is approved.

Frontend needs:

- None required initially. Admin readiness display may be deferred to Phase 7 or Phase 8.

Impeccable required:

- Only if a Web restore/drill UI is scoped later.

Tests needed:

- Backup manifest validation.
- Restored media checksum verification.
- Worldline/conversation/presentation/memory reference resolution.
- Provider config without resolved secrets.
- OpenSpec/docs inclusion check.
- No storage path, raw prompt, raw output, bytes, base64, local path, or secret leak in reports.

Stop conditions:

- Restore requires resolved secrets.
- Restore reports need storage paths or raw object payloads.
- Media/object restore cannot be verified through safe object refs and checksums.
- Drill target cannot be isolated from the developer's active local database/object store.

Can start as-is?

- Needs checkpoint. Decision target: fresh local/single-host restore profile with empty target database and empty object storage root. Staging restore remains optional later scope.

Likely migration needs:
