# v0.7.8 Production Readiness Gate Plan

## Goal

Create an internal production-readiness gate that aggregates existing v0.7 hardening evidence without becoming a public launch gate or duplicate release framework.

This phase is backend/API/test/docs focused. It should give platform admins a safe readiness report over existing beta, release, eval, diagnostics, provider, budget, storage, and security-regression evidence.

## Scope

- Add production-readiness aggregation under `backend/packages/observability/`.
- Reuse the existing observability API router:
  - `backend/services/api/src/noveland/services/api/observability.py`
  - preferred route: `GET /observability/readiness/production`
- Aggregate safe evidence from existing records and services:
  - `BetaChecklistRun` and `BetaChecklistItem`
  - `LongRunEvalRun`
  - `LivingWorldReleaseProfile`
  - provider health checks and provider governance status
  - provider budget policies and emergency stop status
  - storage integrity audit summary
  - runtime diagnostics and incident summary
  - multimodal eval evidence
  - narrative quality dashboard evidence
  - v0.7 security regression suite evidence by documented test references
- Return safe status, blocker/recommendation lists, evidence refs, counts, timestamps, and suppressed-field names only.
- Keep the first version read-only. Do not persist operator signoff unless an existing release/eval record can safely carry it without changing schema.

## Non-goals

- Public launch gate
- Marketing/release workflow
- External compliance certification
- Blocking every runtime path
- New product runtime behavior
- New migrations or readiness tables
- Full vault/KMS, provider marketplace, streaming, daemon execution, or public reader delivery
- Web dashboard or new e2e UI scenarios
- Broad `worlds.py` or `runtime.py` route growth

## Architecture Decision

Use `noveland.observability` as the owner for production-readiness aggregation.

The readiness gate is cross-cutting, but it is an internal platform-admin diagnostic report. Reusing the existing observability package/router avoids broadening `worlds.py`, avoids a new production-hardening catchall package, and keeps readiness output aligned with the safe evidence-ref model from Phase 6.

The first implementation is read-only. Persistent operator signoff is deferred because adding signoff state would either overload release profile metadata or require a new schema; neither is needed to satisfy internal readiness aggregation.

## Expected Migration

No migration is expected.

Stop if implementation requires new readiness tables, historical backfill, or schema changes to release/eval records.

## Deliverables

- Production-readiness contracts/service under `noveland.observability`.
- Platform-admin-only readiness endpoint under `/observability`.
- Safe readiness report with sections, blockers, recommendations, evidence refs, and suppressed-field metadata.
- Focused tests for aggregation, redaction, ACL, and no duplicate release framework.
- Updated OpenSpec task status and harness docs after implementation.

## Guardrails

- Do not expose resolved provider secrets.
- Do not expose raw prompts, raw outputs, prompt snapshots, storage URIs, filesystem paths, bytes, or base64.
- Do not expose readiness reports to world members, readers, players, or unauthenticated routes.
- Do not duplicate beta checklist, long-run eval, release profile, multimodal eval, narrative quality, diagnostics, or security-regression frameworks.
- Do not write readiness reports into `world_events.payload`.
- Keep readiness distinct from public launch readiness.

## Stop Conditions

- Readiness reporting requires raw prompt/output, prompt snapshot body, storage URI, file path, bytes, base64, or resolved secret exposure.
- Existing evidence cannot be summarized without a new persisted readiness schema.
- Implementation drifts into public launch readiness, marketing release workflow, Web UI, daemon execution, or broad route refactors.
- Targeted tests or the full local gate fail.

## Targeted Tests

- Readiness report aggregates beta checklist, long-run eval, and release profile evidence.
- Readiness report aggregates incident, storage, provider, budget, multimodal, narrative quality, and security regression evidence as safe refs/counts.
- Missing evidence creates actionable blockers and recommendations.
- Platform-admin ACL is enforced; lower-privilege actors are denied without leak content.
- Response text excludes resolved secrets, raw prompts, raw outputs, storage URIs, filesystem paths, bytes, and base64.
- No new release/eval/readiness persistence framework is introduced.

## Validation

- Targeted production readiness tests.
- `openspec validate --changes --strict`
- `openspec validate --specs --strict`
- Full local gate before fast-forward merge.
