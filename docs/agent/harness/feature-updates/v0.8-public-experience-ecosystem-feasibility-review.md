# v0.8 Public Experience & Ecosystem Feasibility Review

Date: 2026-05-15
Branch: `main`

## Review Scope

This review confirms the completed v0.7 Production Hardening acceptance state and adapts the proposed v0.8 Public Experience & Ecosystem OpenSpec plan to the current repository. It is documentation and planning only. It does not implement backend, Web, migration, provider, daemon, or public delivery behavior.

## Completed Baseline

- v0.6 Runtime Narrative Quality is complete locally and still active in OpenSpec until archived.
- v0.7 Production Hardening is complete locally and still active in OpenSpec until archived.
- Latest v0.7 full local gate passed with backend ruff, backend mypy over 256 source files, backend pytest (`415 passed, 7 skipped`), Web lint, Web typecheck, Web tests (`112 passed`), Web build, Web `check:next-env`, Web e2e (`13 passed`), docker compose config, and `git diff --check`.
- `main` is clean and ahead of `origin/main`; no push is performed by this review.

## Current Capability Map For v0.8 Planning

- Reader narrative publication already exists through published narrative artifacts and reader-visible publication filtering.
- Media object download already exists for world-scoped admin/member media routes, but it is not a public or reader-safe media delivery contract.
- Conversation turn presentation, visual resolver, speech assets, and multimodal diagnostics are implemented and must be reused.
- Player choice, journal, notification, and intervention records already exist; v0.8 player interaction work must reuse them rather than inventing replacement records.
- Worldline state, snapshot/replay, and comparison-adjacent records exist, but reader-safe worldline browsing still needs explicit DTO and ACL boundaries.
- Plugin catalog and binding validation exist; provider/package work must build on plugin/provider registry and secret governance, not create a marketplace or direct secret path.
- v0.7 internal production readiness exists under observability; v0.8 public launch readiness must aggregate it instead of replacing it.

## Plan Fitness

The v0.8 roadmap is feasible, but the old skeleton was too generic for implementation. The first implementation step should not be a UI surface. It should be a public/read-only contract inventory plus reader-safe media delivery design checkpoint. Conversation playback and galgame scene view should depend on that reader-safe media contract.

The plan should also acknowledge completed v0.7 boundaries:

- internal production readiness is available and must be a prerequisite for public launch;
- secret/provider governance, storage integrity auditing, cost/rate controls, security regression, and incident diagnostics are in place;
- public/reader-facing APIs still need their own explicit safe DTO boundary.

## Recommended v0.8 Order

Keep the 11 planned phases, but make the first phase API/backend-first and require a feasibility checkpoint before implementation:

1. Reader Media Delivery: public/read-only contract inventory, safe media descriptors, delivery endpoint policy, and no storage path leak.
2. Conversation Playback UI: only after reader media delivery exists.
3. Player Interaction UI: reuse existing player choice, journal, notification, and intervention records.
4. Worldline Browser: start with read-only browsing/comparison; destructive rollback needs explicit later approval.
5. Scene View / Galgame View: build on presentation DTOs and reader-safe media.
6. Player Privacy & Data Controls: export/request workflows with shared-world safeguards.
7. World Packaging: safe manifests and preview/apply import discipline.
8. Plugin/Provider Package Contract: package metadata and safety review, no marketplace.
9. Sample World Release Package: build on Phase 13 fixture and world packaging.
10. Moderation & Incident Workflow: requires schema/API decision before implementation.
11. Public Launch Gate: aggregate v0.7 production readiness plus privacy, moderation, sample-world, and public-surface evidence.

## Stop Conditions For v0.8 Implementation

- Unclear public reader authentication model.
- Any design that exposes `storage_uri`, filesystem paths, bytes, base64, raw prompts, raw outputs, or resolved secrets to reader/member APIs or `world_events.payload`.
- Any broad new route growth in `worlds.py`.
- Any duplicate media/provider/eval/readiness framework.
- Any automatic provider spend, daemon execution, streaming, or marketplace scope.
- Any worldline isolation uncertainty for visual, presentation, player, package, or publication data.
- Any migration requirement not described in the phase checkpoint.

## Open Architecture Decisions Before Phase 1 Implementation

- Whether first-cut reader media delivery is authenticated-reader only, member-readable, or public unauthenticated.
- Whether delivery uses direct application streaming, short-lived opaque media tokens, or both.
- Which media visibility fields become authoritative for reader access across assets, objects, references, and narrative publications.
- Whether moderation/report records need a new dedicated package/router in Phase 10.
