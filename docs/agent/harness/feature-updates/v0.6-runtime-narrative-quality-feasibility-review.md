# v0.6 Runtime Narrative Quality Feasibility Review

Date: 2026-05-15

## Scope

This review evaluates the OpenSpec change `v0-6-runtime-narrative-quality` against current `main` after v0.5. It is review-only: no backend or Web implementation is included.

## Current Capability Map

- Runtime context already exists in partial form through `LivingWorldContextSelector`, agent prompt memory context, conversation memory config, and `prompt_snapshots.prompt_context_snapshot_json`.
- GM proposal state already exists through `gm_agendas`, `gm_event_proposals`, macro planning, low-risk deterministic draft creation, offscreen queue items, and worldline forking support.
- Style and continuity review already exist through `gm_style_reviews`, `narrative_continuity_reviews`, and `LivingWorldGuardrailService`.
- Conversation, visual, and speech presentation state exists through `conversation_turn_presentations`, visual sprite/background resolvers, voice profiles, style mappings, transcripts, and multimodal diagnostics.
- Narrative generation already exists through `ConversationNarrativeWriterService`, narrative artifacts, publications, living-world context injection, and publication continuity review.
- Pacing-related primitives exist through conversation policies, runtime daemon batch limits, offscreen queue resolution, asset generation policies, media jobs, and release profile `worldline_policy`.
- Route and relationship state exists through relationship edges, relationship repair records, route affinities, route milestones, ending candidates, player choices, and beta checklist evidence.
- Long-run eval storage already exists through `long_run_eval_runs`; multimodal eval already reuses it.
- Admin diagnostic surfaces already exist for multimodal diagnostics, invocation ledger, provider/media/visual/speech admin, and long-run/beta endpoints in `worlds.py`.

## Cross-Cutting Feasibility Findings

v0.6 is feasible, but the current OpenSpec phase order needs revision before implementation.

The biggest provider conflict is that the Phase 5-8 provider kernel has `ProviderKind.TEXT_GENERATION` contracts and fake text execution, but no real OpenAI/OpenAI-compatible text-generation adapter. Current runtime agent/narrative code still uses the older `noveland.adapters.ProviderProfileService` path. New v0.6 provider-backed GM or narrative work must not expand the legacy path; it should use `ProviderExecutionService` and the Phase 8 secret boundary. Therefore a provider text execution alignment step is needed before real provider-backed GM/narrative generation.

The biggest worldline conflict is that `narrative_artifacts` does not have a first-class `worldline_id`. Some current paths store worldline evidence in metadata or infer it from source conversations/runs, but v0.6's "worldline, visibility, reader-safe filtering" goal is stronger than that. Narrative Writer v2 should stop for an explicit schema decision before implementation.

The biggest API boundary conflict is `worlds.py` size. v0.6 should not add more large runtime quality routes to `worlds.py`. Prefer a dedicated package/router such as `backend/packages/narrative_quality/` and `backend/services/api/src/noveland/services/api/narrative_quality.py`, while reusing existing models/services.

## Phase Feasibility

### Phase 1 — Runtime Context Contract v2

Feasible first.

Recommended scope:
- Add typed context DTOs/services for agent, conversation, GM, narrative, and eval contexts.
- Reuse `LivingWorldContextSelector`, `MemoryService`, conversation services, observations, and prompt snapshots.
- Store `context_kind` and safe context summary inside existing JSON fields rather than adding columns.

Migration: not needed initially.

Risk: do not create a generic context blob that bypasses visibility rules.

### Phase 2 — Provider-backed GM Proposal

Feasible only after provider text execution alignment.

Recommended scope:
- First add/confirm text-generation execution support in the Phase 5-8 provider kernel.
- Then generate `GMEventProposal` records with `model_invocation_id` stored in safe `source_context` or metadata.
- Apply remains explicit and uses existing GM proposal apply/review semantics.

Migration: avoid initially by using `gm_event_proposals.source_context`; add a migration only if a direct FK to `model_invocations` is required.

Blocker: real text-generation adapters are not implemented in the provider kernel today. Do not use the legacy provider profile path for new v0.6 work.

### Phase 3 — Dialogue Style & OOC Review

Feasible and partially covered.

Recommended scope:
- Reuse `GMStyleReview` for `source_kind="conversation_turn"` or a new quality service that writes the same table.
- Attach evidence to admin diagnostics, not reader/member responses.
- Keep provider-backed review optional until text provider alignment is complete.

Migration: not needed initially.

Potential merge: can be implemented together with Continuity Review v2 as a shared review-service foundation.

### Phase 4 — Emotion/Sprite/Voice Alignment

Feasible.

Recommended scope:
- Reuse `conversation_turn_presentations`, `VisualResolver`, `SpeechStyleMappingService`, voice bindings, sprite variants, and `MultimodalEvalService`.
- Return suggestions as diagnostics or eval findings first.
- Do not automatically modify sprite variants, voice bindings, presentation rows, or media references.

Migration: not needed initially.

Risk: suggestions must validate same-worldline media and must not expose storage paths.

### Phase 5 — Narrative Writer v2

Feasible, but should not start until the narrative artifact worldline decision is made.

Recommended scope:
- Reuse narrative services, events, provider invocation ledger, and living-world context filtering.
- Move new provider-backed generation onto `ProviderExecutionService`, not legacy `ProviderProfileService`.
- Define reader-safe output filtering before adding new publish paths.

Migration: likely required if v2 needs first-class `worldline_id` on `narrative_artifacts` and possibly `narrative_publications`.

Blocker: current `narrative_artifacts` are world-scoped but not strict-worldline scoped.

### Phase 6 — Continuity Review v2

Feasible and partially covered.

Recommended scope:
- Extend `NarrativeContinuityReview` issue generation for causality, timeline, relationship jump, route conflict, and secret leakage.
- Reuse `LivingWorldContextSelector.select_for_review()`, world events, route/relationship records, and multimodal diagnostics.
- Keep repair suggestions review-only.

Migration: not needed initially; use `issues` and `metadata` JSON.

Potential merge: can share implementation with Dialogue Style & OOC Review.

### Phase 7 — Runtime Pacing Controller

Feasible later, but not ideal early.

Recommended scope:
- Start as policy preview and diagnostics only.
- Reuse conversation policy, runtime batch limits, offscreen queue, and `asset_generation_policies`.
- Do not connect new automatic daemon behavior in the first implementation.

Migration: likely required if persistent worldline runtime pacing policies are needed. Avoid overloading release profile `worldline_policy` for active runtime control.

Risk: this can accidentally become hidden automatic spend or runtime auto-generation. Keep it after quality diagnostics and provider boundaries are stable.

### Phase 8 — Route & Relationship Progression Quality

Feasible.

Recommended scope:
- Reuse relationship edges, repair records, route affinities, milestones, ending candidates, choices, events, and beta eval evidence.
- Produce explainable drift/progression diagnostics first.
- Do not replace existing relationship model semantics.

Migration: not needed initially.

### Phase 9 — Long-run Living World Simulation Eval

Feasible.

Recommended scope:
- Reuse `LongRunEvalRun` and extend eval keys/metrics.
- Use deterministic sample scenarios before provider-backed live runs.
- Record blockers/recommendations as safe JSON evidence.

Migration: not needed initially.

Risk: avoid making long-run eval block all runtime paths initially.

### Phase 10 — Narrative Quality Dashboard/API

Feasible after review/eval signals exist.

Recommended scope:
- API-first unless the user explicitly requests Web.
- Reuse `LongRunEvalRun`, multimodal eval diagnostics, runtime diagnostics, and v0.4 admin API patterns.
- If Web is later added, use v0.4 admin foundation components.

Migration: not needed initially.

Risk: do not expose raw prompts, prompt snapshots, storage paths, secret evidence, or admin-only diagnostics to reader/member routes.

## Recommended Revised Order

1. Runtime Context Contract v2.
2. Provider Text Execution Alignment for the provider kernel.
3. Provider-backed GM Proposal, proposal-only.
4. Dialogue/OOC + Continuity Review shared review foundation.
5. Emotion/Sprite/Voice Alignment diagnostics.
6. Narrative Artifact Worldline Decision and Narrative Writer v2.
7. Route & Relationship Progression Quality.
8. Runtime Pacing Controller, preview/diagnostics first.
9. Long-run Living World Simulation Eval.
10. Narrative Quality Dashboard/API.

This keeps the current 10-phase size by merging dialogue/OOC and continuity review into one shared review foundation and adding the missing provider text alignment step.

## Migration Plan

No migration initially:
- Runtime context contracts if stored in existing prompt snapshot/context JSON.
- GM proposal invocation linkage if stored in `source_context`.
- Dialogue/OOC review if reusing `gm_style_reviews`.
- Continuity review if reusing `narrative_continuity_reviews`.
- Emotion/sprite/voice alignment diagnostics if using eval/diagnostic records.
- Route/relationship progression diagnostics if using eval/diagnostic records.
- Long-run eval if reusing `long_run_eval_runs`.
- Dashboard/API if backed by existing eval/diagnostic records.

Likely migration:
- Narrative Writer v2 if strict `worldline_id` is added to `narrative_artifacts` and/or `narrative_publications`.
- Runtime Pacing Controller if persistent worldline pacing policy requires its own table.

Migration decision needed:
- Whether to add direct FK links from GM proposals or narrative drafts to `model_invocations`, or keep IDs in safe JSON evidence.

## Reuse Requirements

Must reuse:
- `ProviderExecutionService`, `ProviderRegistryService`, `ProviderSecretResolver`, invocation ledger, and prompt snapshots.
- `LivingWorldContextSelector`, `LivingWorldGuardrailService`, `ConversationService`, `ConversationRuntimeOrchestrator`, and `AgentRuntimeOrchestrator`.
- `GMEventProposal`, `GMAgenda`, offscreen queue, route/relationship tables, and beta/release evidence records.
- `NarrativeArtifactService`, narrative publications, and existing publication guardrail review.
- `conversation_turn_presentations`, visual resolver, speech style mapping, voice binding/profile services, and multimodal eval diagnostics.
- `LongRunEvalRun`, runtime diagnostics, and v0.4 admin API patterns.

Must not reuse:
- Legacy `noveland.adapters.ProviderProfileService` for new v0.6 provider-backed features.
- `world_events.payload` for raw prompts, raw outputs, storage paths, bytes, or provider secrets.
- `narrative_artifacts` as media storage.

## Deferred Items

- Web dashboard work unless explicitly requested after API/data contracts stabilize.
- Runtime daemon auto-generation or hidden automatic spend.
- Automatic high-impact GM apply.
- Automatic narrative repair apply.
- Provider fallback/load balancing.
- Public reader quality dashboard or media delivery.
- Full production observability/exporter.

## Stop Conditions Before Implementation

Stop before v0.6 implementation if any of these remain unresolved:

- Provider text-generation adapter boundary in the provider kernel.
- Narrative artifact worldline strategy.
- Whether v0.6 gets a dedicated `narrative_quality` package/router.
- Whether GM proposal invocation linkage remains safe JSON evidence or gets a schema FK.
- Any plan to add broad new routes to `worlds.py`.

## Recommendation

Do not start v0.6 implementation from the current OpenSpec unchanged. First update the v0.6 OpenSpec design, phase plan, tasks, and affected specs to reflect:

- Provider text execution alignment before provider-backed GM/narrative work.
- Narrative artifact worldline decision before Narrative Writer v2.
- Dedicated narrative quality package/router for new v0.6 APIs.
- API-first quality diagnostics before Web dashboard work.
