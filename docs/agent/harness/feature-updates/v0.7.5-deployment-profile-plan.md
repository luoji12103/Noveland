# v0.7.5 Deployment Profile Plan

## Goal

Define a repeatable local and single-host production-like deployment profile using the health, migration, and verification commands that already exist.

This phase is docs/test focused. The optimized scope is to document and validate the supported operator flow, not to add new runtime endpoints or a new production-hardening router.

## Scope

- Expand `docs/agent/operations/deployment-profile.md` into a complete operator guide for:
  - local compose startup order
  - environment variable inventory and required refs
  - migration procedure
  - rollback prerequisites
  - health and verification commands
- Cross-link existing operator docs:
  - `docs/agent/operations/runtime-supervision.md`
  - `docs/agent/operations/runtime-recovery.md`
  - `docs/agent/operations/backup-restore.md`
  - `docs/agent/architecture/configuration-and-secrets.md`
- Add a lightweight documentation regression test that confirms the deployment profile doc covers the expected local/single-host commands and non-goals.
- Validate the current local deployment commands and health checks without introducing managed-cloud lock-in.

## Non-goals

- Managed-cloud platform lock-in
- Kubernetes orchestration
- Autoscaling
- New runtime or provider endpoints
- New production-hardening router/package
- Migration/schema changes
- Secret vault or encrypted DB secret storage
- Web UI
- Broad `worlds.py` growth

## Current Baseline

- `infra/compose.yaml` already defines the local PostgreSQL/pgvector and NATS JetStream stack.
- `GET /health`, `GET /runtime/supervision`, `GET /runtime/status`, `GET /provider-profiles/health`, and `GET /metrics` already exist.
- `alembic current`, `alembic upgrade head`, `noveland-backup-verify`, and `noveland-runtime --once` already exist as local operator checks.
- Provider secret refs already resolve through environment/settings boundaries; deployment profile docs should describe the supported refs, not persist new secrets.

## Architecture Decision

Use existing runtime, provider, storage, and migration surfaces only.

No new API router is expected for Phase 5. If implementation requires a new runtime or deployment endpoint, stop and re-review the architecture instead of expanding the phase.

## Expected Migration

No migration is expected.

Stop if implementation requires persisted deployment state, a schema change, or a new operational router.

## Deliverables

- Expanded deployment profile operator doc.
- Small docs regression test for required commands and non-goals.
- Updated harness bookkeeping for the phase start and phase completion.

## Guardrails

- Do not expose resolved secrets, storage URIs, filesystem paths, bytes, base64, raw prompts, or raw outputs.
- Do not add a managed-cloud-specific deployment path.
- Do not add a new deployment router/package unless an explicit architecture decision is made first.
- Do not change runtime behavior just to satisfy documentation.

## Stop Conditions

- A new endpoint or router becomes necessary.
- The deployment profile would need managed-cloud assumptions.
- The phase requires migration or persisted deployment state.
- The documentation cannot accurately reflect current behavior without changing runtime semantics.

## Targeted Tests

- Deployment profile doc includes compose startup, migration, health, backup, and rollback commands.
- Deployment profile doc includes the supported local/single-host environment variables and refs.
- Deployment profile doc preserves the managed-cloud and Kubernetes non-goals.
- Existing runtime health and provider health tests remain passing.
