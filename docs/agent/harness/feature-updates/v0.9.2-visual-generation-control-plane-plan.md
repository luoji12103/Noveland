# v0.9.2 Visual Generation Control Plane Plan

Date: 2026-05-16
Branch: `feat/v0.9-visual-generation-control-plane`

## Goal

Implement v0.9 Phase 2 only: create a dedicated Visual Generation Control Plane that safely plans image generation across ComfyUI, Z-Image, GPT Image, OpenAI-compatible image APIs, and generic image providers without letting runtime agents execute arbitrary workflow payloads.

This checkpoint is docs-only. It does not implement backend behavior, Web behavior, migrations, API routes, or runtime contract changes.

## Package and Router Ownership

Decision: add a dedicated package and router for implementation.

- Package: `backend/packages/visual_generation/`
- Router: `backend/services/api/src/noveland/services/api/visual_generation.py`
- Router registration: app-level registration only.
- Forbidden placement: no broad `worlds.py` routes, no ownership inside `backend/packages/visual/`, `backend/packages/asset_generation/`, `backend/packages/providers/`, or `backend/packages/media/`.

Ownership boundary:

- `visual_generation` owns workflow templates, template versions, visual model inventory, character/worldline visual generation profiles, provider-neutral visual generation plans, slot validators, and image-provider mapping contracts.
- `providers` owns actual provider adapter execution.
- `media` owns resulting files, assets, objects, references, and storage boundaries.
- `visual` owns applied sprite/background bindings and resolver behavior.
- `authoring` owns galgame source import, proposal, review, and apply workflows.
- `asset_generation` owns existing background/lookahead generation proposals/jobs.
- `invocations` owns model-call audit, prompt snapshots, tags, and redaction.

## First Migration Scope

Decision: Phase 2 implementation is expected to add a migration. Do not start implementation until a branch-specific migration checkpoint confirms exact column names, indexes, and foreign keys.

First implementation tables:

- `visual_workflow_templates`
- `visual_workflow_template_versions`
- `visual_model_assets`
- `character_visual_generation_profiles`

Migration principles:

- Do not store raw uncontrolled execution payloads as the only representation.
- Admin-only template version payloads may preserve raw ComfyUI/API-format workflow JSON or provider request templates, but execution must always derive from template version plus validated slots.
- Use explicit world/worldline fields for every table where plans, profiles, inventory, or references can affect world state.
- Add indexes for `world_id`, `worldline_id`, `provider_id`, `character_id`, template key/version, inventory kind, status, and review state as applicable.

## Workflow Template Safety Model

Decision: workflow templates are pre-registered, versioned, and slot-validated.

Required behavior:

- Templates expose validated parameter slots.
- Runtime agents may not execute arbitrary raw ComfyUI workflow JSON.
- AI may propose bindings, profiles, prompt presets, or workflow variants only as reviewable proposals.
- Persistent workflow/profile/template changes require explicit review/apply.
- Execution requires provider capability validation and template slot validation before any provider adapter call.
- Workflow validation errors are stored as safe metadata and must not expose local paths, storage paths, resolved secrets, or provider internals to reader/player/member APIs.

ComfyUI rationale:

- ComfyUI's official route documentation describes `/prompt` as validating a submitted prompt/workflow before adding it to the execution queue and returning either queue metadata or validation errors including `node_errors`.
- ComfyUI cloud API documentation describes submitted workflows as JSON nodes and connections.
- Noveland should therefore keep an auditable template/slot boundary before submission instead of treating workflow payloads as arbitrary agent-authored text.

Reference links:

- https://docs.comfy.org/development/comfyui-server/comms_routes
- https://docs.comfy.org/api-reference/cloud/workflow/submit-a-workflow-for-execution

## Visual Model Inventory Model

Decision: use world-scoped provider inventory records for provider-local model listings and worldline-scoped profile bindings for character-specific usage.

First-supported inventory kinds:

- `checkpoint`
- `lora`
- `vae`
- `embedding`
- `controlnet`
- `ip_adapter`
- `workflow_template`
- `prompt_preset`
- `other`

Required fields:

- `world_id`
- nullable `worldline_id` for inventory records
- `provider_id`
- `inventory_kind`
- `display_name`
- `provider_model_name` or `file_name`
- `trigger_words`
- `compatible_base_models`
- `recommended_weight`
- `style_tags`
- `character_tags`
- `visibility`
- `source_license_note`
- `metadata_json`

Worldline decision:

- Inventory records are world-scoped by default because provider-local checkpoint/LoRA/model listings usually belong to a configured provider and should not be duplicated per branch.
- Inventory records may include a nullable `worldline_id` only when a model asset is intentionally branch-specific.
- Character visual generation profiles are strict worldline-scoped because visual state and character appearance may diverge across worldlines.
- Local model file paths, storage paths, and provider-local filesystem details must never be reader-visible.

Decision: character visual generation profiles are strict worldline-scoped.

Profiles must support:

- `character_id`

- `worldline_id`

- allowed LoRAs
- default LoRAs

- negative prompt fragments
- reference asset ids

Profiles guide planner choices. They do not grant agents permission to choose arbitrary models, LoRAs, references, workflows, or provider payloads.

## Provider-neutral Plan DTO

Decision: every provider-backed image generation attempt starts with a provider-neutral visual generation plan.

Canonical plan fields:

- `intent`
- `provider_id`
- `workflow_template_id`
- `character_ids`
- `scene_id`
- `prompt_plan`
- `model_plan`
- `reference_assets`
- `output_plan`
- `validation_results`
- `source_context`
- resulting media refs after execution

Plan execution must:

- validate same world and worldline;
- validate provider capability;
- validate template slots;
- validate model inventory choices;
- validate reference asset visibility;
- write invocation ledger records for provider-backed calls;
- write media assets and media objects for outputs;
- preserve links from plan to invocation and resulting media;
- never write storage URI, filesystem path, object storage path, S3/GCS URL, bytes, base64, raw prompt, raw output, prompt snapshot internals, or resolved secrets into `world_events.payload` or reader/player/member APIs.

## ComfyUI Mapping Policy

Decision: ComfyUI receives only a filled workflow generated from a registered template version and validated slots.

Rules:

- Raw workflow JSON may be stored only as a versioned admin-only template payload.
- Runtime execution must derive from template plus validated slots.
- Runtime agents cannot pass arbitrary workflow JSON to execution.
- Slot validation must reject non-whitelisted node/parameter changes.
- Model, LoRA, checkpoint, sampler, seed, image size, reference image, mask, control image, prompt, negative prompt, and output-node choices must be validated against template schema, provider capabilities, inventory records, and profile policy.
- ComfyUI validation errors must be stored as safe metadata and redacted before API response.
- Custom node and model path details must not be exposed to reader/member/player APIs.

## Cross-provider Mapping Policy

Decision: provider-neutral visual generation plans map into provider-specific adapter inputs only after capability validation.

Mapping targets:

- ComfyUI: template slots become a filled workflow/prompt payload for the ComfyUI adapter.
- Z-Image: prompt and output plan map to the configured Z-Image-compatible request shape; unsupported edit, LoRA, workflow, mask, or reference fields are rejected or safely ignored according to capability policy.
- GPT Image: prompt, output plan, and allowed reference assets map to generation/edit inputs supported by the configured adapter.
- OpenAI-compatible image: prompt/output/reference fields map to compatible image-generation or image-edit endpoints where capability metadata permits.
- Generic image/custom HTTP: provider-specific request JSON is assembled from whitelisted template slots only.

Unsupported fields must never pass through silently when they could change safety, worldline, reference, or spend behavior. The implementation should prefer explicit validation issues for unsupported workflow, LoRA, reference, mask, control, edit, or output-format fields.

## AI Proposal Policy

Decision: AI may propose visual configuration, but may not automatically execute or apply it.

Allowed AI proposals:

- visual generation profiles;
- workflow bindings;
- prompt presets;
- workflow variants based on existing templates;
- reference-asset recommendations;
- model/LoRA/checkpoint recommendations constrained by inventory.

Proposal rules:

- Proposals must be reviewable and traceable.
- Persistent changes require explicit admin review/apply.
- Workflow variants must be versioned and validated.
- Only whitelisted node or parameter changes are allowed for variants.
- Proposed variants must not execute automatically.
- Proposals preserve source traceability and model invocation linkage when provider-backed.
- The first implementation may use authoring proposals or visual_generation-owned proposals, but it must not bypass preview/review/apply.

## Frontend Decision

Decision: Phase 2 implementation should be backend/API-first plus minimal admin diagnostics only.

Allowed Web scope if needed:

- list workflow templates;
- inspect inventory;
- inspect profile summaries;
- inspect plan validation result summaries;
- trigger explicit test/dry-run flows only if backend validation is already complete.

Deferred Web scope:

- rich workflow editor;
- ComfyUI graph editor;
- freeform node editing;
- custom node installation UI;
- model downloader;
- automatic profile/workflow apply.

Frontend rule:

- If Phase 2 implementation includes Web UI, Codex must read and use `impeccable` before implementation.
- Keep any UI operator-grade, dense, explicit, and aligned with existing admin surfaces.

## Targeted Test Strategy

Targeted tests for implementation:

- workflow template create/update/list;
- workflow template version validation;
- slot schema validation;
- rejection of non-whitelisted slots;
- rejection of arbitrary runtime workflow JSON;
- visual model inventory create/update/list/filter;
- LoRA compatibility, allowed/default/banned LoRA, and checkpoint compatibility validation;
- character visual profile create/update/list and worldline validation;
- provider-neutral plan creation and validation;
- ComfyUI template slot mapping with fake/mock adapter;
- Z-Image, GPT Image, OpenAI-compatible image, and generic image mapping validation with fake/mock providers;
- cross-world and cross-worldline reference rejection;
- hidden/developer-only/private inventory and media reference suppression;
- safe API response redaction;
- no leak of storage URI, path, bytes, base64, raw prompt, raw output, raw workflow JSON, or resolved secret;
- provider-backed execution records invocation ledger and resulting media refs;
- `world_events.payload` never receives forbidden provider/media/prompt fields.

Default tests must not call real providers. Real ComfyUI/Z-Image/GPT Image checks belong to the later provider lab profile and must remain opt-in.

## Stop Conditions

Stop implementation if:

- schema ownership conflicts with providers, media, visual, authoring, or asset_generation;
- workflow execution requires arbitrary raw ComfyUI workflow JSON;
- model inventory requires exposing local file paths to reader/player/member APIs;
- character visual profile worldline semantics become unclear;
- provider-neutral plans cannot validate provider capabilities;
- ComfyUI, Z-Image, GPT Image, OpenAI-compatible image, or generic image mapping cannot be represented safely;
- AI proposal apply path bypasses review/apply;
- persistent workflow/profile changes would happen without explicit admin approval;
- real provider tests would run by default;
- broad `worlds.py` route growth becomes necessary;
- frontend work is required but `impeccable` cannot be read and used.
