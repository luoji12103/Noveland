# v1.0.1 Private Beta Onboarding & Access Model Plan

## Scope

This is the docs-only Phase 1 checkpoint for `openspec/changes/v1-0-private-beta-mvp/`.
It does not implement backend behavior, Web behavior, migrations, route registration, runtime
behavior, API behavior, or provider calls.

Phase 1 implementation may begin only after this checkpoint is accepted.

## Repository Findings

- `WorldMembership` currently stores only `world_id`, `user_id`, and `role`; the role vocabulary
  is limited to `world_admin` and `human_user`.
- `authorization.py` already supports deny-by-default world access: non-members receive a safe
  not-found response, and non-admin members receive forbidden responses for admin paths.
- `PlayerActorProfile` is already `world_id` plus `worldline_id` plus `user_id` scoped, which is
  the right target for guided player identity setup after a tester has valid private beta access.
- Existing membership APIs live in `worlds.py`, but Phase 1 private beta onboarding must not add
  broad onboarding routes there.

Conclusion: `WorldMembership` is suitable as the enforcement layer after invitation redemption,
but it is not sufficient as the invitation lifecycle or audit model.

## Decisions

### 1. Invitation Model

Decision: use a dedicated private beta invite/access table. Do not use membership-only access for
Phase 1.

`WorldMembership` cannot represent pending, accepted, waitlisted, redeemed, expired, and revoked
states; inviter audit; token redemption audit; expiry; revocation reason; or beta-specific role
metadata without overloading a coarse enforcement table. Private beta access therefore needs its
own package and table, with membership creation or update happening only after a valid redemption.

The first implementation should keep the schema minimal:

- primary table: `private_beta_invites`;
- no separate persistent template or signup table;
- optional future audit table only if append-only lifecycle history proves necessary.

### 2. Package And Router Ownership

Decision:

- Add `backend/packages/private_beta/`.
- Add `backend/services/api/src/noveland/services/api/private_beta.py`.
- Register the router at the app level only.
- Do not add broad private beta onboarding routes to `worlds.py`.

Expected package contents for first implementation:

- `contracts.py` for invite, redemption, onboarding, and safe tester DTOs;
- `models.py` for the invite/access table;
- `service.py` for lifecycle, redemption, least-privilege membership bootstrap, and player profile
  onboarding orchestration;
- `security.py` or equivalent helpers for token hashing, safe fingerprints, and redaction if the
  implementation needs a separate module.

Planned route shape:

- Admin invite management:
  - `GET /worlds/{world_id}/private-beta/invites`
  - `POST /worlds/{world_id}/private-beta/invites`
  - `POST /worlds/{world_id}/private-beta/invites/{invite_id}/revoke`
- Tester redemption:
  - `POST /private-beta/invites/redeem`
- Tester onboarding:
  - `GET /private-beta/onboarding`
  - `POST /worlds/{world_id}/private-beta/onboarding/player-profile`

The redemption endpoint should accept the token in a request body, not in a query string. A Web
redeem page may use a URL fragment or a short-lived local form value so the raw token is not sent
through server logs before the explicit redemption POST.

### 3. Access Lifecycle

Decision: Phase 1 uses a finite invite lifecycle with these states:

- `pending`: invite is issued, valid, and awaiting tester redemption.
- `waitlisted`: tester candidate exists but cannot redeem until an admin changes state.
- `accepted`: admin-approved candidate or invite is eligible to redeem before expiration.
- `redeemed`: token was redeemed by an authenticated user and access bootstrap completed or can
  safely resume.
- `expired`: invite is past expiration and cannot be redeemed.
- `revoked`: invite was revoked by an authorized admin and cannot be redeemed.

Allowed redemption states are `pending` and `accepted`, subject to expiration and world checks.
`expired`, `revoked`, `waitlisted`, and already-redeemed records must not create additional
privileges. Repeated redemption of the same valid invite should be idempotent only for the same
authenticated user and same world; otherwise it should be safely rejected.

### 4. First Migration Plan

Expected first migration: `private_beta_invites`.

Planned fields:

- `id`
- `world_id`
- `worldline_id` nullable
- `invited_email` nullable
- `invited_user_id` nullable
- `token_hash`
- `status`
- `intended_world_role`, defaulting to `human_user`
- `beta_role`, for example `tester` or `player_tester`
- `expires_at`
- `accepted_at` nullable
- `redeemed_at` nullable
- `redeemed_by_user_id` nullable
- `revoked_at` nullable
- `revoked_by_actor_ref` nullable
- `revocation_reason` nullable
- `created_by_actor_ref`
- `metadata_json`, safe and redacted
- `created_at`
- `updated_at`

Constraints and indexes should cover:

- token hash uniqueness;
- world/status listing;
- invited user lookup;
- invited email lookup where supported;
- valid status values;
- intended membership role limited to least-privilege roles for beta testers.

`worldline_id` remains nullable because some invites are world-level. If it is present, onboarding
must restrict player profile creation to that worldline. If it is absent, guided onboarding must
resolve a valid worldline before creating `PlayerActorProfile`.

### 5. Relationship With WorldMembership

Decision: invite redemption may create or update `WorldMembership`, but membership is not the
source of invite lifecycle truth.

Rules:

- Deny by default before redemption.
- Redemption may create a `WorldMembership` with role `human_user`.
- Redemption must not create `world_admin`, platform admin, provider admin, invocation admin, or
  media admin privileges.
- Redemption must not silently upgrade an existing user to a higher privilege.
- If an invited user already has elevated access through another path, the beta flow must still
  return only tester-safe DTOs and must not use that elevation as part of onboarding.
- Tester/member APIs must not expose provider configuration, resolved secrets, prompt snapshot
  internals, invocation raw prompts or outputs, storage URIs, filesystem paths, object paths,
  bytes, base64, hidden assets, or `developer_only` assets.

### 6. Player Actor/Profile Bootstrap

Decision: create access first, then create the `PlayerActorProfile` through guided onboarding.

Raw invite redemption should establish safe private beta access and least-privilege membership.
The first-run onboarding step should collect or confirm player display name, player identity
fields, and worldline selection before creating or reusing the `PlayerActorProfile`.

This avoids manual database edits while preserving the current strict worldline scope of
`PlayerActorProfile`.

### 7. Frontend Scope

Decision: Phase 1 implementation should be API-first plus a minimal Web redemption flow.

Do not build a full onboarding product tour or marketing-style onboarding. The first Web scope, if
approved during implementation, should be:

- invite redemption page;
- safe onboarding entry state;
- player identity/profile setup;
- private beta world selection limited to eligible worlds;
- concise first-run guidance with recovery expectations.

Any Web implementation must use `impeccable` before coding. For this checkpoint, the Noveland
product context was read: product register, calm/operator-grade UI, dense operational workflows,
no marketing SaaS styling, no decorative hero flow, and WCAG AA expectations.

### 8. Security Model

Phase 1 implementation must require:

- deny-by-default beta access;
- least privilege for all tester roles;
- non-guessable invite tokens generated with strong randomness;
- token hash storage only;
- raw token returned at most once to an authorized admin during invite creation;
- no raw token in logs, prompt snapshots, model invocations, `world_events.payload`, reader APIs,
  player APIs, member APIs, or admin list responses;
- revoked and expired invites cannot be redeemed;
- idempotent redemption only where the same user, invite, world, and state make it safe;
- tester responses use safe DTOs only;
- no public signup dependency.

### 9. Test Strategy

Targeted Phase 1 tests should cover:

- authorized admin can create an invite;
- non-admin cannot create an invite;
- invite list responses do not include raw tokens;
- valid invite redemption creates least-privilege access;
- expired invite redemption is rejected;
- revoked invite redemption is rejected;
- waitlisted invite redemption is rejected;
- repeated redemption is idempotent for the same user or safely rejected;
- redemption cannot create `world_admin`;
- guided onboarding creates or reuses `PlayerActorProfile` in the authorized world/worldline;
- cross-world invite use is rejected;
- worldline handling is validated when `worldline_id` is present;
- tester cannot access admin, provider, invocation ledger admin, or media admin routes;
- tester cannot see hidden or `developer_only` assets through private beta DTOs;
- API responses do not leak token, secrets, storage paths, filesystem paths, object paths, bytes,
  base64, raw prompts, raw outputs, or prompt snapshot internals.

### 10. Stop Conditions

Stop implementation if:

- a membership-only model is still proposed without lifecycle and audit justification;
- public signup becomes required;
- tester onboarding requires admin, provider, invocation, or media-admin privileges;
- invite tokens would be stored or logged in plaintext;
- access cannot be deny-by-default;
- implementation requires broad `worlds.py` route growth;
- tester DTOs require exposing provider configuration, prompt snapshot internals, raw prompts,
  raw outputs, storage paths, filesystem paths, object paths, bytes, base64, or resolved secrets;
- worldline selection or `PlayerActorProfile` ownership is unclear;
- Web UI is required but `impeccable` cannot be read and used.

## Implementation Recommendation

Phase 1 can proceed after this checkpoint is accepted, with a first implementation slice that adds
the `private_beta` package, app-level router, `private_beta_invites` migration, lifecycle service,
safe redemption contract, guided player profile bootstrap, and targeted ACL/redaction tests.

Do not continue to Phase 2 until Phase 1 implementation, targeted tests, full local gate, OpenSpec
validation, harness updates, and fast-forward merge are complete.
