# v0.8.8 Plugin/Provider Package Contract Plan

## Status

Planned for implementation after v0.8 Phase 7 World Packaging passed the full local gate and fast-forward merged to local `main`.

## Goal

Add a safe package contract boundary for plugin/provider metadata, capability declarations, config export, and safety review without adding marketplace behavior, secret handling, or runtime installation of untrusted code.

## Scope

- Backend/API-only first implementation.
- Represent package metadata and capability declarations as validation contracts.
- Validate plugin package declarations against the existing builtin plugin registry.
- Validate provider package declarations against existing provider capability and adapter concepts.
- Export safe provider config templates from existing provider integrations without resolved secrets.
- Report safety review status for package metadata and exported config.
- Reuse existing plugin registry, provider registry/capabilities, provider secret governance, and v0.7 redaction rules.

## Proposed Boundary

- Package: `backend/packages/package_contracts/`
- API router: `backend/services/api/src/noveland/services/api/package_contracts.py`
- Route prefix: `/worlds/{world_id}/package-contracts`

This route is world-admin scoped. It is separate from `worlds.py`, admin media routes, and reader/player routes.

## First API Shape

- `POST /worlds/{world_id}/package-contracts/validate`
- `GET /worlds/{world_id}/package-contracts/provider-config-export`

The first endpoint validates submitted package metadata without persistence. The second endpoint exports safe provider integration config summaries for admin package review.

## Contract Shape

Package metadata may include:

- `package_key`, `version`, display name, description, publisher ref, and safety notes.
- Plugin declarations: plugin identifier, category, version, capabilities, and config schema/template.
- Provider declarations: provider kind, adapter kind, capability keys, config template, default params template, and optional opaque `auth_ref`.
- Safety review status: `draft`, `pending_review`, `approved`, `blocked`.

Contract responses must include issues and warnings rather than throwing opaque stack traces.

## Secret And Config Safety

The validator must reject or redact sensitive keys recursively using the Phase 8/v0.7 provider secret boundary:

- `api_key`, `apikey`, `token`, `bearer_token`, `authorization`, `secret`, `client_secret`, `access_key`, `password`, `private_key`

Safe config export may include opaque `auth_ref` references such as `env:OPENAI_API_KEY`, but must not resolve or expose secret values. Exported config must not include storage paths, raw prompts, raw outputs, bytes, base64, or prompt snapshot internals.

## Migration Decision

No migration for Phase 8 first implementation. Package contract validation and provider config export are response-only. If a later phase needs persisted package reviews or marketplace-style registry records, stop and add a dedicated migration plan first.

## Tests

- Package metadata validates known plugin categories and provider kinds.
- Unknown plugin identifiers and category mismatches return actionable issues.
- Provider capability declarations validate against existing provider capability keys when provider integrations are present.
- Sensitive keys are rejected recursively in plugin config, provider config, default params, and safety notes.
- Provider config export includes opaque `auth_ref` and excludes resolved secrets.
- Provider config export sanitizes storage paths, raw prompt/output markers, bytes/base64, and prompt snapshot markers.
- Unsafe packages are blocked pending review.
- ACL requires world admin access.
- Existing plugin catalog and provider routes remain unchanged.

## Guardrails

- No provider marketplace.
- No runtime plugin installation.
- No user-managed secret UI.
- No provider execution.
- No daemon jobs or automatic spend.
- No Web UI.
- No broad `worlds.py` route growth.
- No storage URI, filesystem path, object storage path, bytes/base64, raw prompt/output, prompt snapshot internals, or resolved secrets in responses.
